# Документация строительной ИТД-экосистемы

**Рабочая ветка:** `docs/itd-specification`  
**Статус:** проектная документация; наличие документа не означает, что описанная функция реализована.

## 1. Продукты и границы

- **Приложение ИТД:** самостоятельное Windows-приложение. Основной продуктовый контур.
- **Строительные ИИ-агенты:** независимая платформа в отдельном репозитории `construction-ai-agents`; подключается к ИТД, другим приложениям и ИИ-системам.
- **Сметный контур:** самостоятельное будущее направление; интеграция с ГРАНД-Смета учитывается, но не задерживает основной релиз ИТД.
- **Старая бизнес-панель:** `biznes-panel-psd` — исходный прототип и архив истории, не целевой продуктовый репозиторий.

## 3. Порядок чтения

Для проверки основного продукта читать в первую очередь ТЗ v0.6, затем архитектуру и регламенты. Макеты и история нужны для контекста и подтверждения происхождения отдельных решений. Если краткая сводка расходится с ТЗ v0.6 или более поздним прямым решением пользователя, применять более позднее и детальное требование.

## 4. Статусы документов

- **APPROVED / Утверждено** — решение прямо подтверждено пользователем.
- **BASELINE / Базовая редакция** — документ подготовлен для целостной проверки.
- **PROPOSED / Предложение** — рекомендация, не утверждённая пользователем.
- **NEEDS_SOURCE / Требует исходника** — нужен эталонный файл, нормативный источник или доказательство.
- **NOT_VERIFIED / Не проверено** — проверка ещё не выполнялась.

## 5. Принципы рабочего процесса

- Не выводить промежуточные макеты и мелкие изменения пользователю.
- Предоставлять цельный документ для проверки и коррекции.
- Спрашивать только при принципиальном выборе, который нельзя безопасно сделать по уже утверждённым требованиям.
- Отмечать места повышенного риска и не углубляться в необязательные функции до завершения основного ИТД.
- Не менять `main` и не смешивать документационную ветку с реализацией.
- Не заявлять о готовности кода, сборки, тестов или выпуска без фактического подтверждения.
