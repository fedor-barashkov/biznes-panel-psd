# SP-02 — спецификация технического spike безопасного локального IPC

**Версия:** 0.1  
**Дата:** 2026-11-10  
**Статус:** спецификация эксперимента; прототип и испытания не выполнены.  
**Родительский документ:** P0_TECHNICAL_FINDINGS_v0.1.md.

## 1. Цель

Проверить, может ли независимый Runtime на Windows безопасно принимать локальные запросы от приложения ИТД и других доверенных desktop-клиентов без открытия сетевого порта и без административных прав для обычного запуска.

Spike не реализует Runtime, авторизацию всей платформы или производственные операции. Это изолированный технический прототип транспорта и идентификации локального клиента.

## 2. Гипотезы

- H1: Named Pipe может быть создан обычным пользователем и доступен только разрешённому security principal.
- H2: другой локальный пользователь не может читать/писать канал.
- H3: клиентская идентичность может быть проверена на стороне сервера, а не принята из поля JSON.
- H4: транспорт корректно обрабатывает конкурентные клиенты, malformed/oversized сообщения, timeout, cancellation и разрыв соединения.
- H5: канал не доступен через удалённый SMB/сетевой путь.
- H6: контрактный слой не зависит от конкретного IPC транспорта.

## 3. Состав прототипа

Два небольших Windows console executables или один проект с режимами server/client:

- Pipe Server — создаёт локальный Named Pipe, применяет явный security descriptor, принимает сообщения и записывает технический аудит.
- Pipe Client — отправляет запрос с версией контракта, correlation ID и тестовой полезной нагрузкой.
- Unauthorized Client — отдельный тестовый сценарий, который пытается подключиться из неразрешённого контекста.
- Test Harness — автоматизирует проверки и сохраняет доказательства.

Никакого доступа к пользовательским документам, SQLite ИТД, ГРАНД-Смете, shell, HTTP или облачным моделям.

## 4. Требования безопасности

1. Pipe name имеет префикс LOCAL и уникальный идентификатор продукта/экземпляра.
2. Используется явный DACL; security descriptor не оставляется NULL/default.
3. ACL выдаёт только минимальные необходимые права определённому пользователю или logon SID.
4. Проверяется клиентский security token/identity на серверной стороне. Поле actor/user из JSON не считается доказательством.
5. При невозможности проверить principal соединение отклоняется (fail closed).
6. Сервер не принимает путь к файлу, shell-команду, URL или произвольный вызов метода.
7. Ограничены максимальный размер сообщения, число параллельных клиентов, время чтения и время обработки.
8. Протокол имеет явную версию и тип сообщения; неизвестные версии/типы отклоняются.
9. Ошибки не раскрывают ACL, SID, токены, системные пути или внутренние секреты.
10. Удалённый доступ должен быть запрещён и доказан отдельным тестом. Не считать обычный PipeSecurity/ACL достаточным доказательством: в публичном PipeOptions .NET 10 нет отдельного флага PIPE_REJECT_REMOTE_CLIENTS. Проверить managed ACL с запретом NT AUTHORITY\\NETWORK и native CreateNamedPipeW с PIPE_REJECT_REMOTE_CLIENTS (0x00000008); если используется native interop, отдельно проверить SafePipeHandle lifecycle и защиту от pipe-name squatting.
11. Каждый запрос получает operation/correlation ID; аудит фиксирует подключение, principal, решение и итог без секретов.
12. Канал не считается полной авторизацией: запрос после IPC всё равно должен пройти Task Intake, schema validation и PDP/PEP.

## 5. Протокол тестового сообщения

Минимальный логический конверт:
- protocol_version;
- message_type;
- request_id;
- correlation_id;
- client_instance_id;
- payload.

Тестовый payload содержит только harmless echo/health operation. Идентичность клиента устанавливается отдельно из Windows security context. Не добавлять в payload access token или доверенный actor role.

Ответ:
- protocol_version;
- request_id;
- correlation_id;
- status;
- error_code (если есть);
- server_instance_id.

Конкретный wire encoding выбирается в ходе spike. Он должен поддерживать framing: одно сообщение не может поглотить следующее, частичное чтение не должно считаться полным сообщением.

## 6. Матрица испытаний

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| IPC-001 | Сервер запускается от обычного пользователя | Успешно, без UAC/admin elevation |
| IPC-002 | Разрешённый клиент того же пользователя подключается | Успешный health/echo round trip |
| IPC-003 | Другой локальный пользователь подключается | Отказ на уровне ACL или серверной проверки |
| IPC-004 | Клиент подменяет actor/user в JSON | Подмена игнорируется; principal берётся из OS context |
| IPC-005 | Клиент без разрешённого security token | Fail-closed отказ |
| IPC-006 | Попытка удалённого подключения | Отказ; канал не экспортируется в сеть |
| IPC-007 | Неизвестная версия протокола | Контролируемый отказ, сервер остаётся работоспособен |
| IPC-008 | Некорректный JSON/бинарный фрейм | Отказ одного запроса, процесс не падает |
| IPC-009 | Сообщение больше установленного лимита | Отказ до неограниченного выделения памяти |
| IPC-010 | Клиент прекращает соединение посреди сообщения | Освобождение ресурсов, корректный статус |
| IPC-011 | Тайм-аут клиента/сервера | Отмена операции без зависания процесса |
| IPC-012 | Несколько параллельных разрешённых клиентов | Нет смешивания ответов/correlation ID |
| IPC-013 | Перезапуск сервера | Клиент обнаруживает недоступность и может безопасно переподключиться |
| IPC-014 | Клиент повторяет запрос с тем же request_id | Транспорт не выполняет бизнес-действие; дублирующий запрос виден тестовому harness |
| IPC-015 | Секрет/поддельный токен в payload | Не влияет на identity/ACL; не попадает в аудит |
| IPC-016 | Сканирование локальных pipe names | Нет выдачи чувствительных данных через диагностические ответы |

Каждый тест фиксирует Windows version/build, .NET runtime, SID/logon context, результат и воспроизводимые логи. Негативные тесты должны доказывать отказ, а не просто отсутствие исключения.

## 7. Критерии завершения

SP-02 получает PASS только если:
- все IPC-001—IPC-016 имеют PASS и воспроизводимые доказательства;
- проверены как минимум два разных локальных security principal;
- сервер работает без административных прав;
- ACL выставлен явно и проверен независимым тестом;
- нет удалённого доступа;
- нагрузочные/конкурентные тесты не смешивают запросы;
- протокол версионирован и не зависит от бизнес-логики;
- независимый QA просмотрел код, конфигурацию и доказательства.

Если Windows CI не может проверить разные локальные учётные записи или сетевой сценарий, соответствующие тесты маркируются BLOCKED, а не PASS. Управляемые API .NET и native Win32 варианты, их ограничения и проверенные сигнатуры сведены в [SP-02_DOTNET_IMPLEMENTATION_NOTES_v0.1.md](SP-02_DOTNET_IMPLEMENTATION_NOTES_v0.1.md). Нужна отдельная ручная проверка на тестовой Windows VM/машине.

## 8. Результаты и артефакты

После выполнения spike должны быть подготовлены:
1. исходный код прототипа в независимом репозитории construction-ai-agents;
2. инструкция запуска server/client;
3. тестовые сценарии и автоматизированные Windows integration tests;
4. журнал тестов с версиями ОС и .NET;
5. threat notes и ограничения;
6. ADR IPC-01: выбрать Named Pipes, выбрать иной транспорт или отклонить подход;
7. список требований к production IPC adapter.

Не помещать этот прототип в ITD product code или ветку старой бизнес-панели. Если независимый репозиторий ещё не создан, хранить только эту спецификацию в документационной ветке; исходный код не размещать в несоответствующем продукте.

## 9. Ограничения

Успех SP-02 доказывает только пригодность транспорта для локального IPC. Он не доказывает:
- полную аутентификацию пользователя или авторизацию бизнес-действий;
- защиту от администратора/скомпрометированной учётной записи;
- корректность PDP/PEP, approval, nonce или audit store;
- безопасность удалённого relay;
- возможность облачного ChatGPT/Codex напрямую обращаться к локальному процессу;
- готовность Runtime к производственному использованию.

**Итог:** SP-02 — ограниченный security-oriented prototype. Он должен предшествовать реализации общего API Gateway, но не заменяет платформенную модель безопасности.
