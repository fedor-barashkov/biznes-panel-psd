# План реализации Runtime MVP строительных ИИ-агентов

**Версия:** 0.1  
**Дата:** 2026-11-10  
**Статус:** план работ; реализация не начата.  
**Основание:** RUNTIME_ARCHITECTURE_v0.1.md и связанные спецификации платформы.

## 1. Назначение

Документ переводит архитектуру Runtime в управляемый backlog: последовательность работ, зависимости, результаты и критерии завершения. План не утверждает технологический стек и не разрешает переход к внешней записи/выпуску документов.

Базовое правило: сначала проверяемая инфраструктура и безопасный локальный контур, затем агентные workflow, после этого клиентские адаптеры. Не начинать реализацию всех ролей и интеграций одновременно.

## 2. Правила выполнения

1. Работы выполняются в отдельном целевом репозитории construction-ai-agents после его создания; до этого документы остаются в текущей документационной ветке.
2. Не менять main и не сливать staging PR без отдельного решения.
3. Каждый этап начинается с входных критериев и заканчивается артефактами, тестами и QA-отчётом.
4. Неизвестный технологический выбор закрывается коротким spike и ADR, а не предположением.
5. Каждый кодовый компонент имеет контракт, тесты, журналируемые ошибки и документацию подключения.
6. Любая новая функция должна иметь негативный тест: что произойдёт при отказе, нехватке прав, конфликте версии или повреждённом входе.
7. Пока не пройдены security gates, разрешены только read-only и draft операции.
8. QA не считается независимым только потому, что отдельный prompt назван QA: независимость должна обеспечиваться runtime-политикой, раздельными principals и тестами.

## 3. Очерёдность этапов

| Этап | Результат | Разрешённый режим |
|---|---|---|
| P0 — Technical Spikes | ADR и измерения для ключевых технических решений | Исследования и прототипы |
| P1 — Runtime Foundation | Локальное ядро, API, задачи, артефакты, аудит и восстановление | Read-only / draft |
| P2 — Agent Workflow | Маршрутизация ГИП/ПТО/QA, QA-цикл и approvals | Read-only / draft; approval только тестовый до security gate |
| P3 — Security Gate | Реальные identity, PDP/PEP/PIP, permits, nonce, транзакции и защищённый аудит | Ограниченные тестовые write-действия |
| P4 — Client Adapters | ИТД, офисные форматы, Excel Автогенератор и тестовый Grand Smeta | Только разрешённые адаптером действия |
| P5 — Hardening / Release | Установка, обновление, резервирование, восстановление и выпуск | Кандидат в пользовательский MVP |

P3 — обязательный gate до любой производственной записи, экспорта, выпуска или передачи.

## 4. P0 — Technical Spikes

### SP-01. Windows lifecycle и deployment
- Исследовать отдельный процесс/службу, запуск от пользователя, остановку, перезапуск и обновление.
- Проверить работу без административных прав там, где это возможно.
- Измерить время старта, потребление памяти и поведение при аварийном завершении.
- Результат: ADR с вариантом упаковки и воспроизводимым прототипом.

### SP-02. Local API / IPC
- Сравнить локальные варианты транспорта и безопасную привязку клиента к локальному пользователю.
- Проверить запрет неавторизованного локального клиента и изоляцию сессий.
- Результат: ADR, тестовый клиент и threat notes.

### SP-03. Metadata store и файловые артефакты
- Сравнить локальные варианты хранилища по транзакциям, блокировкам, миграциям, резервному копированию и восстановлению.
- Проверить хранение крупных PDF/DOCX/XLSX отдельно от метаданных.
- Результат: ADR, тест на конкурентное изменение и тест восстановления.

### SP-04. Identity, keys и audit
- Исследовать локальную идентичность, защищённое хранилище ОС, криптографическую проверку permit, nonce и append-only аудит.
- Определить fail-closed поведение при недоступности аудита или хранилища ключей.
- Результат: security ADR, прототип проверки разрешения и негативные тесты.

### SP-05. Model Gateway и privacy
- Сравнить провайдерный интерфейс, поддержку тайм-аутов/лимитов и возможность локальной модели.
- Составить матрицу классов данных: что можно отправлять конкретному провайдеру, что запрещено, что требует согласия.
- Результат: ADR, тестовый провайдерный адаптер и политика передачи данных.

### SP-06. File ingestion
- Проверить PDF/DOCX/XLSX, сканы и OCR на реальных обезличенных примерах.
- Измерить извлечение таблиц, координат/листов, страниц и локаторов.
- Проверить лимиты размера, повреждённые файлы и недоверенное содержимое.
- Результат: ADR, benchmark-набор и протокол ошибок извлечения.

### SP-07. Contract compatibility
- Проверить текущие JSON Schema, fixtures и business validator как входную границу runtime.
- Определить правила version negotiation и backward compatibility.
- Результат: контрактные тесты и ADR по управлению версиями.

### Gate P0
P0 завершён, когда все spike имеют ADR, альтернативы, измерения, риски и прототипные доказательства. Необходимо отдельное решение об утверждении стека. Само завершение spike не означает утверждение архитектуры без просмотра результатов.

|---|---|---|---|
| RT-F01 | Репозиторий, структура модулей, CI и правила версий | P0, создание репозитория | Воспроизводимая сборка, тесты и проверка формата |
| RT-F02 | Contract Validator | RT-F01 | Все запросы/ответы валидируются до действий; fixtures проходят CI |
| RT-F03 | Task Intake и idempotency | RT-F02 | Дубликаты не создают повторные задачи; конфликт ключа отклоняется |
| RT-F04 | Task State Store | RT-F03, SP-03 | Состояния и переходы транзакционны и восстанавливаются после рестарта |
| RT-F05 | Artifact Registry | SP-03, RT-F01 | Артефакт, редакция, hash, provenance и связи доступны через API |
| RT-F06 | Local Artifact Storage | SP-03, RT-F05 | Исходники неизменяемы; доступ проходит через сервис с проверкой scope |
| RT-F07 | Audit Event Writer | SP-04, RT-F04 | События состояния и операций связаны по correlation ID; секреты исключены |
| RT-F08 | Local Gateway | SP-02, RT-F02 | Тестовый клиент создаёт задачу и получает состояние/результат |
| RT-F09 | Agent Registry | RT-F02 | Роль, версия, схема и допустимые инструменты регистрируются явно |
| RT-F10 | Execution Manager | RT-F04, RT-F08, RT-F09 | Запуск, timeout, cancellation и безопасный restart подтверждены тестами |
| RT-F11 | Model Gateway | SP-05, RT-F10 | Один провайдер подключён через интерфейс; отказ провайдера не маскируется |
| RT-F12 | Diagnostics | RT-F04, RT-F07 | Диагностический пакет показывает ошибки и версии без секретов |

### Gate P1
- пройдены RT-001—RT-009, RT-012 и RT-016 в применимой части;
- runtime запускается на чистой Windows-среде;
- работает без сети для локальных операций;
- нет внешних write/export инструментов;
- резервная копия восстановлена в отдельном тестовом каталоге;
- QA подтверждает трассировку требований к тестам и результатам.

## 6. P2 — Agent Workflow

| ID | Работа | Зависимости | Результат и критерий завершения |
|---|---|---|---|
| WF-01 | Workflow DSL / graph model | P1 | Workflow версионируется; неизвестные переходы запрещены |
| WF-02 | Router | WF-01, RT-F09 | Задача попадает только в разрешённую роль; неоднозначность требует уточнения |
| WF-03 | Skills Registry | RT-F09 | Навыки имеют schemas, permissions, versions и тесты |
| WF-04 | GIP workflow adapter | WF-02, WF-03 | Анализ ПД/РД и draft ВОР с доказательствами |
| WF-05 | PTO workflow adapter | WF-02, WF-03 | Draft ИД по утверждённому шаблону, без выдуманных фактов |
| WF-06 | QA Gate | WF-01, WF-03 | QA читает зафиксированную редакцию, автор не может менять QA findings |
| WF-07 | Revision / rework loop | WF-06, RT-F05 | Исправление создаёт новую редакцию; повторная проверка регистрируется |
| WF-08 | Approval Manager (test mode) | WF-01, RT-F07 | Тестовые human approval records связаны с точным artifact/revision/action |
| WF-09 | Workflow observability | WF-01, RT-F07 | Пользователь видит timeline, ожидания, блокировки и причины |
| WF-10 | Golden test corpus | WF-04—WF-07 | Эталонные строительные кейсы, негативные кейсы и регрессия |

### Gate P2
- ГИП, ПТО и QA проходят свои ролевые golden tests;
- QA независим по principal и read-only доступу;
- QA_FAILED возвращает исполнителю конкретные findings;
- новая редакция проходит повторную проверку;
- approval в тестовом режиме не даёт производственных полномочий;
- все неизвестные факты и отсутствующие исходные данные остаются явными.

## 7. P3 — Security Gate

| ID | Работа | Зависимости | Результат и критерий завершения |
|---|---|---|---|
| SEC-R01 | Local Identity Provider | SP-04, P1 | Подтверждённый human/service/agent principal |
| SEC-R02 | PIP attribute resolver | SEC-R01 | Проверяемые атрибуты клиента, проекта, объекта и ресурса |
| SEC-R03 | PDP policy engine | SEC-R02 | Решения по actor/action/resource/scope/policy version |
| SEC-R04 | PEP enforcement | SEC-R03, RT-F10 | Каждый защищённый tool call перепроверяет permit |
| SEC-R05 | Signed permit / nonce | SP-04, SEC-R03 | Permit ограничен действием, редакцией, сроком и одноразовым nonce |
| SEC-R06 | Atomic operation executor | SEC-R04, RT-F04 | Проверка версии, применение операции и потребление nonce атомарны |
| SEC-R07 | Append-only audit integrity | SP-04, RT-F07 | Целостность событий проверяется; отказ аудита блокирует protected action |
| SEC-R08 | Revocation / expiry | SEC-R05 | Отозванное/просроченное разрешение не исполняется |
| SEC-R09 | Security regression suite | SEC-R01—SEC-R08 | Replay, scope escape, forged human, stale revision и bypass тесты |

### Gate P3
Запись/экспорт запрещены, пока все SEC-R тесты не пройдены и QA не подтвердил доказательства. Дополнительно требуется отдельное человеческое решение о включении конкретных write/export операций и конкретных адаптеров. Успех P3 не означает автоматическое разрешение всех операций.

## 8. P4 — Клиентские адаптеры

1. **ITD Adapter:** начать с чтения карточек объекта, подобъектов, организаций, шаблонов и документов. Запись черновика — после отдельного scope/approval теста.
2. **Office/File Adapter:** импорт PDF/DOCX/XLSX и экспорт черновиков. Не подменять оригиналы; сохранять исходный файл и результат извлечения отдельно.
3. **Excel Автогенератор Adapter:** сначала аудит книги и контракт обмена, затем тестовый импорт/экспорт на копии. Формулы, макросы, листы и именованные диапазоны фиксируются.
4. **Grand Smeta Adapter:** сначала изучить поддерживаемые официальные интерфейсы/форматы версии 2026, затем read-only/test exchange. Round-trip сравнивает коды, шифры, названия норм, единицы, количества, коэффициенты и структуру. Производственная запись требует отдельного approval.
5. **AI Client Adapter:** реализовать контракт подключения для нескольких ИИ-клиентов, не раскрывая им внутреннюю БД и локальные секреты.

Для каждого адаптера отдельны спецификация, permissions, threat review, contract tests, compatibility matrix и rollback plan.

## 9. P5 — Hardening и пользовательский выпуск

- установщик и проверка подписи;
- обновление с резервной копией и откатом;
- тест восстановления после повреждения данных и отключения питания;
- проверка производительности на объёмах реальных документов;
- аудит приватности и retention;
- пользовательская документация, диагностика и экспорт отчёта;
- независимый QA релиз-кандидата;
- отдельная пользовательская приёмка.

## 10. Definition of Done для любой задачи

Задача не закрывается без:
1. ссылки на требование и архитектурный компонент;
2. согласованного интерфейса/схемы;
3. реализации либо явно оформленного результата spike;
4. позитивного и негативного теста;
5. обработки ошибок, timeout и отмены, если применимо;
6. логирования без секретов;
7. документации и версии;
8. результата CI или воспроизводимого локального теста;
9. независимой QA-проверки;
10. явного статуса PASS/FAIL/BLOCKED/NOT_RUN.

## 11. Главные риски и меры

| Риск | Мера |
|---|---|
| Слишком ранний выбор стека | P0 spike и ADR до реализации |
| Смешение ядра и ИТД | Независимый API и клиентские адаптеры |
| Prompt injection из документов | Изоляция недоверенного контента и тесты |
| Утечка документов в облачную модель | Матрица приватности, allowlist провайдеров, минимизация контекста |
| Повторное выполнение внешней операции | Idempotency, operation ID, сверка результата и nonce |
| Ложное подтверждение полномочий | Human-only identity, PDP/PEP и signed permit |
| Потеря доказательств/источников | Immutable artifacts, provenance и QA gate |
| Перерастание MVP в большой монолит | Этапы P0—P5 и запрет включать будущие интеграции в P1 |
| Непроверенные обещания о работе | Тестовые статусы и доказательства по каждому gate |

## 12. Что не следует делать до завершения P0/P1

- Не выбирать язык/фреймворк по привычке без сравнительного spike.
- Не строить микросервисы и облачную инфраструктуру для первого локального MVP.
- Не давать агентам произвольный доступ к диску, сети, shell или БД.
- Не реализовывать массовую запись в ИТД/ГРАНД-Смета.
- Не смешивать сметный контур с основным MVP ИД.
- Не переносить документы и исходники пользователя в публичный репозиторий без проверки конфиденциальности и прав.
- Не объявлять платформу готовой после одной успешной сборки или демонстрации.

**Итоговый статус:** план декомпозирует реализацию Runtime на проверяемые этапы и work packages. Это backlog и критерии управления работами, а не подтверждение существования runtime или выполнения указанных задач.
