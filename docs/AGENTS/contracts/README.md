# Машинно-читаемые контракты

Версия набора: **0.1**  
Формат: JSON Schema Draft 2020-12  
Статус: первая формализованная редакция; автоматическая проверка настроена через GitHub Actions, результат выполнения workflow должен быть проверен отдельно.

## Состав схем

| Схема | Назначение |
|---|---|
| [task-envelope.schema.json](schemas/task-envelope.schema.json) | Универсальный запрос клиента к агенту |
| [agent-response.schema.json](schemas/agent-response.schema.json) | Ответ агента, доказательства, неопределённости и предлагаемые действия |
| [artifact-manifest.schema.json](schemas/artifact-manifest.schema.json) | Метаданные результата/артефакта, контрольная сумма и происхождение |
| [approval-record.schema.json](schemas/approval-record.schema.json) | Запись решения уполномоченного человека по действию |
| [qa-report.schema.json](schemas/qa-report.schema.json) | Отчёт независимого QA, проверки, замечания и вердикт |

## Ролевые схемы и тестовые примеры

Ролевые схемы уточняют общие транспортные контракты и не заменяют их:
- ГИП: ВОР отделяет извлечённые, рассчитанные, интерпретированные и неопределённые объёмы; расчётная позиция требует метода, выражения и источника.
- ПТО: структура полей определяется переданным эталонным шаблоном; схема хранит ID полей, источники, статус заполнения и приложения, но не навязывает собственную форму АОСР.
- Сметчик: позиция связана с исходной позицией ВОР; отдельно фиксируются нормативная база, коды, наименования, единицы, количества, коэффициенты и преобразования обмена.
- QA: фиксируются независимость, критерии, методы, доказательства и вердикт. Сам по себе schema-valid отчёт не доказывает фактическое прохождение проверки.

В `fixtures/` находятся четыре положительных (`*.valid.json`) и четыре отрицательных (`*.invalid.json`) примера для ролевых схем. Проверка выполняется скриптом `scripts/validate_agent_contracts.py`; GitHub Actions workflow — `.github/workflows/validate-agent-contracts.yml`. Workflow использует `jsonschema[format]==4.25.1` и Draft 2020-12.

## Общие правила

- Схемы описывают транспортные данные и не предоставляют сами по себе доступ к операциям.
- Идентификаторы объектов клиента непрозрачны; права проверяет клиентский адаптер/сервер.
- Ссылки на файлы не означают разрешение на чтение или изменение.
- Поля происхождения и доказательств фиксируют источник, но не гарантируют истинность источника.
- Подписание, отправка, выпуск, изменение статуса приёмки и иные значимые действия требуют отдельного разрешения и человеческого подтверждения.
- `QA_PASSED` — статус прохождения QA-проверок, а не юридическая приёмка или утверждение документа.
- `additionalProperties: false` используется в корневых и критичных вложенных структурах для выявления неизвестных полей; расширение контракта выполняется через версионирование.

## Версионирование и публикация

Набор схем версионируется независимо от версии агента, модели, адаптера и клиентского приложения. Несовместимое изменение обязательных полей или семантики требует новой версии. Перед реализацией runtime схемы должны быть прогнаны валидатором Draft 2020-12, проверены тестовыми примерами и связаны с релизом неизменяемыми версиями.

## Открытые решения

- окончательные канонические URI схем и способ публикации;
- версия валидатора зафиксирована в CI; её обновление требует повторного прогона схем и фикстур;
- стратегия совместимости и миграции;
- правила подписи/проверки контрольных сумм и доверия к артефактам;
- конкретная транспортная реализация (REST, MCP, IPC, stdio или иной вариант).
