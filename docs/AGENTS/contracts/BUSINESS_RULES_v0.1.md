# Бизнес-правила строительных ИИ-агентов

**Версия:** 0.1  
**Статус:** исполняемый прототип валидатора и модульные тесты; не является production runtime или системой цифровой подписи.  
**Расположение кода:** `scripts/agent_business_rules.py`  
**Тесты:** `tests/test_agent_business_rules.py`

## 1. Назначение и границы доверия

JSON Schema проверяет структуру, типы и обязательные поля. Бизнес-валидатор проверяет межполевые зависимости, согласованность связанных записей и допустимость статуса результата.

**Критически важно:** поля результата, созданного агентом, являются недоверенными. Подтверждения полномочий, реестры утверждённых ВОР/шаблонов, записи согласования, авторизация пользователя и результаты обратного сравнения должны поступать валидатору из доверенного контекста клиента/сервера. Нельзя брать эти сведения из самого проверяемого JSON и считать их подтверждёнными.

Валидатор только сообщает нарушения. Он не подписывает документы, не утверждает ВОР, не выпускает ИД, не меняет статусы в клиентской БД и не выполняет экспорт.

## 2. Общие правила

- Неизвестный источник, несоответствие редакции или пустой локатор — блокирующее нарушение для доказательной позиции.
- Нельзя повышать статус результата только на основании значения, присланного агентом.
- Отсутствие подтверждения трактуется как отсутствие разрешения (fail closed).
- Повторный запуск проверки не меняет исходный артефакт.
- Любая бизнес-проверка возвращает машинный код, путь к данным, описание и уровень серьёзности.
- Контекст доверия формируется сервером/клиентским адаптером после проверки пользователя и источников; не принимается напрямую от модели.

## 3. Правила ГИП / ВОР

| Код | Условие |
|---|---|
| GIP_DUPLICATE_POSITION_ID | ID позиции ВОР уникальны |
| GIP_UNDETERMINED_HAS_QUANTITY | Для неопределённого объёма quantity должен быть null |
| GIP_MISSING_QUANTITY | Для определённого происхождения объёма quantity обязателен |
| GIP_CALCULATION_BASIS_MISSING | Расчётная позиция требует метода и формулы |
| GIP_EVIDENCE_RELATION_MISMATCH | Тип происхождения позиции должен соответствовать relation доказательства |
| GIP_EVIDENCE_SOURCE_UNKNOWN | Источник доказательства должен входить в source_documents |
| GIP_EVIDENCE_REVISION_MISMATCH | Редакция и шифр доказательства должны совпадать с зарегистрированным источником |
| GIP_EVIDENCE_LOCATOR_EMPTY | Доказательство должно иметь локатор листа/страницы/узла/фрагмента |
| GIP_APPROVAL_HAS_BLOCKING_ISSUES | Утверждение блокируется при CRITICAL/MAJOR замечаниях |
| GIP_APPROVAL_HAS_OPEN_QUESTIONS | Утверждение блокируется при открытых вопросах |
| GIP_APPROVAL_POSITION_UNVERIFIED | Каждая позиция утверждаемой ВОР должна быть verified |
| GIP_APPROVAL_NOT_AUTHORIZED | Нужна доверенная запись согласования именно этой ВОР и редакции уполномоченным ГИПом |

Черновая ВОР может содержать вопросы и непроверенные позиции. Для `approved_by_gip` требуются отсутствие открытых вопросов, проверенные позиции и совпадающая доверенная запись согласования.

## 4. Правила ПТО / ИД

- Ссылки каждого поля должны указывать на зарегистрированные source_documents.
- Для `approved_for_release` и `released` проверка документа должна быть успешной, список findings пустым, а поля — подтверждёнными либо явно неприменимыми.
- Приложения должны быть приложены либо отмечены как не требующиеся; `missing` и `pending_confirmation` блокируют выпуск.
- ID и редакция шаблона сверяются с доверенным реестром активных утверждённых шаблонов. Агент не может подменить пользовательский образец собственной формой.
- `released` требует отдельной доверенной записи решения уполномоченного лица по ID документа и редакции. Подготовка агентом проекта документа не равна выпуску или подписанию.

## 5. Правила сметчика / ГРАНД-Смета

- Для утверждения/экспорта ВОР сверяется с доверенным реестром по ID, редакции и статусу; одного поля `approved_by_gip` в сообщении агента недостаточно.
- Проверка сохранности должна охватывать коды позиций ВОР/сметы, коды норм, наименования, единицы и количества; если в позициях присутствуют ресурсы или коэффициенты, они также включаются в проверяемый набор.
- Доверенный реестр ВОР должен подтверждать не только ID, редакцию и статус, но и состав `position_ids`; каждая сметная позиция обязана ссылаться на позицию именно этой редакции ВОР.
- Нельзя заявлять `passed=true`, если список `losses_detected` не пуст или если `checked_fields` не покрывает все применимые поля.
- Для статуса `approved` все позиции должны иметь `mapping_status=matched`, отсутствовать открытые вопросы, а утверждение должно быть подтверждено доверенной записью уполномоченного сметчика.
- Для `exported` дополнительно требуется успешное обратное сравнение с результатом `identical` и отдельное доверенное разрешение `grand_smeta.export` на конкретную редакцию сметы (не то же самое, что утверждение сметы). Разрешение должно содержать ID артефакта, редакцию, операцию, исполнителя и ID решения. При любом расхождении экспорт блокируется до анализа и явного решения.

## 6. Правила QA

- Проверяющий должен быть независимым и отличаться от автора проверяемого результата.
- Для `QA_PASSED` все обязательные проверки должны быть `passed` или `not_applicable`; у каждой пройденной проверки должно быть доказательство; непроверенных пунктов быть не должно.
- Незакрытые BLOCKER/CRITICAL/MAJOR запрещают `QA_PASSED`.
- Открытые MINOR допускаются для `QA_PASSED` только при наличии доверенной записи принятия риска с владельцем, ID решения и явным перечнем всех соответствующих `finding_id`.
- Любое замечание со статусом `accepted_risk` требует такой же доверенной записи независимо от того, формируется `QA_PASSED` или `CONDITIONAL_PASS`; агент не может самостоятельно объявить риск принятым.
- `CONDITIONAL_PASS` требует отсутствия незакрытых BLOCKER/CRITICAL, завершённых обязательных проверок, отсутствия непроверенных пунктов и доверенного решения с владельцем риска, явно перечисляющего все принимаемые finding ID.
- `QA_PASSED` означает прохождение набора QA-проверок, но не означает инженерное утверждение, подписание, приёмку работ или разрешение на выпуск документа.

## 7. Доверенный контекст

Прототип ожидает следующие объекты контекста (точная форма должна быть закреплена отдельным API-контрактом runtime):

- `approval_record`: `approval_id`, `artifact_id`, `revision`, `decision`, `actor_id`, `actor_type=human`, `actor_role`, `authorized=true`.
- `export_authorization`: `authorized=true`, `artifact_id`, `revision`, `operation=grand_smeta.export`, `actor_id`, `actor_type=human`, `decision_id`.
- `template_registry`: `template_id`, `revision`, `active`.
- `boq_registry`: `boq_id`, `revision`, `approval_status`, `authorized`, `position_ids` (состав утверждённой редакции ВОР).
- `round_trip_check`: `performed`, `result`.
- `export_authorization`: `authorized`, `artifact_id`, `revision`, `operation`, `actor_id`, `decision_id`.
- `reviewer_agent_id`, `reviewer_independent`.
- `risk_acceptance`: `approved`, `owner_id`, `actor_id` (совпадает с owner_id), `actor_type=human`, `decision_id`, `finding_ids` (все открытые MAJOR/MINOR, а также все findings со статусом `accepted_risk`, принимаемые решением).
- `document_revision`, `estimate_revision`.

Структуры контекста формализованы схемами `gip-approval-context.schema.json`, `pto-release-context.schema.json`, `estimator-approval-context.schema.json` и `qa-review-context.schema.json`; положительные/отрицательные fixtures находятся в `fixtures/`. Это проверка формы, а не готовая модель аутентификации: контекст должен создаваться только доверенным компонентом после проверки полномочий и связываться с неизменяемыми записями аудита.

## 8. Запуск и тестирование

Локально из корня репозитория:

```bash
python -m unittest discover -s tests -p "test_agent_business_rules.py" -v
```

GitHub Actions запускает этот набор после проверки JSON Schema и фикстур. Результат считается подтверждённым только для конкретного commit SHA, на котором workflow завершился успешно.

## 9. Ограничения прототипа

- Валидатор не является сервисом, API, авторизационным сервером или workflow engine.
- Проверка реальности подписи, полномочий и реестров пока делегирована доверенному контексту; интеграция с хранилищем согласований не реализована.
- Нормативная проверка содержания ВОР/АОСР и корректности сметных норм требует предметных модулей и актуальных нормативных источников.
- Обратное сравнение с ГРАНД-Смета должно выполняться адаптером реального формата; здесь проверяется только переданный доверенный результат.
- Перед production необходимо добавить аудит событий, защиту от повторного использования approval record, атомарные переходы статусов и интеграционные тесты адаптеров.
