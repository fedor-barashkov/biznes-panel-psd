# Универсальный контракт интеграции строительных ИИ-агентов

**Версия:** 0.1  
**Статус:** логическая спецификация контракта; транспорт, аутентификация и runtime ещё не выбраны.  
**Связанный документ:** `PLATFORM_SPEC_v0.1.md`.

## 1. Назначение

Контракт задаёт единый способ постановки задач и получения результатов от строительных агентов независимо от того, кто является клиентом: приложение ИТД, Excel-автоматизатор, другая строительная программа, корпоративная система или ИИ-клиент.

Клиент не вызывает внутренние функции агента и не обращается к его внутреннему хранилищу. Он передаёт запрос по контракту и предоставляет только разрешённые инструменты/данные.

## 2. Обязательные принципы

- Версионирование контракта и схем.
- Совместимость ядра агента с несколькими клиентами и ИИ-провайдерами.
- Идентификаторы сущностей клиента непрозрачны для агента; агент использует только предоставленные ссылки и разрешённые операции.
- Любой источник данных имеет стабильный идентификатор и локатор.
- Любое действие имеет область доступа, разрешение и, если нужно, подтверждение.
- Идемпотентность повторного запроса и защита от повторного выполнения.
- Ошибки, неопределённость и неполнота возвращаются явно.
- Никакой прямой записи в БД клиента.
- Схемы и содержимое файлов — данные, а не инструкции, меняющие правила агента.

## 3. Логическая структура запроса

Пример запроса (иллюстративный JSON; реальные имена и схемы утверждаются до реализации):

```json
{
  "contract_version": "0.1",
  "request_id": "client-generated-unique-id",
  "idempotency_key": "stable-key-for-this-operation",
  "agent_id": "construction.pto",
  "task_type": "prepare_aosr_draft",
  "locale": "ru-RU",
  "context": {
    "client_id": "itd-desktop-app",
    "project_id": "project-reference",
    "object_id": "object-reference",
    "subobject_id": "subobject-reference"
  },
  "inputs": [
    {
      "input_id": "input-1",
      "kind": "document_reference",
      "document_id": "document-reference",
      "revision_id": "revision-reference",
      "media_type": "application/pdf",
      "locator": {
        "page": 3
      }
    }
  ],
  "available_tools": [
    {
      "tool_id": "documents.read",
      "scope": ["object-reference"],
      "permissions": ["read"]
    }
  ],
  "approval_policy": {
    "draft_write": "confirm",
    "external_send": "deny",
    "document_release": "deny",
    "acceptance_status_change": "deny"
  },
  "expected_output_schema": "construction.pto.aosr-draft/0.1"
}
```

Обязательные поля: версия контракта, request_id, agent_id, task_type, inputs/context в пределах задачи, разрешённые инструменты, политика подтверждений и ожидаемая схема результата.

Пустой или неизвестный идентификатор не должен трактоваться как доступ ко всему объекту или проекту.

## 4. Логическая структура ответа

```json
{
  "contract_version": "0.1",
  "request_id": "client-generated-unique-id",
  "agent_id": "construction.pto",
  "agent_version": "0.1.0",
  "status": "needs_review",
  "result": {
    "draft_document": {},
    "proposed_field_values": []
  },
  "evidence": [
    {
      "source_document_id": "document-reference",
      "revision_id": "revision-reference",
      "locator": {
        "page": 3,
        "section": "identified-section"
      },
      "excerpt": "short source excerpt",
      "extraction_method": "ocr",
      "verification": "unconfirmed"
    }
  ],
  "assumptions": [],
  "uncertainties": [],
  "warnings": [],
  "proposed_actions": [
    {
      "action_id": "action-1",
      "operation": "documents.save_draft",
      "target": "document-reference",
      "requires_approval": true
    }
  ],
  "requires_human_approval": true
}
```

Ответ различает:
- `completed` — задача завершена без обязательного подтверждения;
- `needs_review` — результат подготовлен, требуется проверка;
- `needs_input` — данных недостаточно, требуется уточнение;
- `blocked` — действие запрещено или отсутствует необходимое право;
- `failed` — задача завершилась ошибкой;
- `partial` — выполнена только часть задачи, остаток перечислен.

Статус агента не должен автоматически менять статус документа, согласования или приёмки в клиентском приложении.

## 5. Доказательства и происхождение

Каждый вывод или значение, существенно влияющее на документ/расчёт, по возможности сопровождается:
- ID исходного документа и его редакции;
- локатором: страница, лист, ячейка, раздел, таблица, фрагмент;
- коротким извлечённым фрагментом или ссылкой на него;
- методом извлечения;
- состоянием подтверждения;
- указанием, является ли значение извлечённым, вычисленным или интерпретированным.

Если точный локатор получить невозможно, агент обязан явно указать это ограничение.

## 6. Предлагаемые действия и подтверждения

Агент может возвращать предложение действия, но выполнение происходит через инструмент клиента с проверкой прав и подтверждения.

Уровни:
1. **Read** — чтение разрешённых источников.
2. **Analyze** — анализ и вычисление в рамках заданных правил.
3. **Draft** — создание черновика или проекта изменений.
4. **Modify** — изменение существующей сущности с контролем версии и сравнением.
5. **Release/Send/Sign/Accept** — выпуск, отправка, подписание, приёмка или иное юридически/операционно значимое действие.

Уровни 4 и 5 требуют отдельных разрешений. Уровень 5 по умолчанию запрещён для автоматического исполнения агентом и требует явного подтверждения уполномоченного пользователя. Агент не может самостоятельно устанавливать статус «Принят».

## 7. Ошибки и конфликты

Стандартные категории:
- `INVALID_REQUEST`;
- `UNSUPPORTED_CONTRACT_VERSION`;
- `UNKNOWN_AGENT`;
- `PERMISSION_DENIED`;
- `SOURCE_NOT_FOUND`;
- `SOURCE_AMBIGUOUS`;
- `SOURCE_CONFLICT`;
- `SCHEMA_VALIDATION_FAILED`;
- `APPROVAL_REQUIRED`;
- `IDEMPOTENCY_CONFLICT`;
- `CLIENT_ADAPTER_ERROR`;
- `MODEL_PROVIDER_ERROR`;
- `TIMEOUT`;
- `INTERNAL_ERROR`.

Ошибка не должна приводить к сообщению об успешном сохранении или выполнении. Повторный запрос с тем же idempotency key не должен создавать дублирующие документы или действия.

## 8. Совместимость и версии

- Версия контракта отделена от версии агента, модели, инструмента, адаптера и схемы результата.
- Совместимые расширения могут добавлять необязательные поля.
- Удаление/переименование обязательного поля или изменение его семантики требует новой несовместимой версии.
- Клиент и платформа согласуют поддерживаемые версии до запуска задачи.
- Адаптер отклоняет несовместимый запрос до выполнения действий.
- Миграция результатов старых версий не должна менять исходные документы.

## 9. Адаптеры

Минимальный набор будущих адаптеров:
- `itd-desktop-app`;
- Excel-автоматизатор ИД;
- ГРАНД-Смета;
- внешние строительные приложения;
- ИИ-провайдеры/модели;
- файловые и документные хранилища.

Каждый адаптер описывает:
- поддерживаемые версии клиента;
- операции и типы данных;
- разрешения и границы доступа;
- ограничения форматов;
- правила обработки конфликтов;
- тестовые сценарии;
- журналирование и обработку ошибок.

Наличие названия адаптера в списке не означает, что он реализован. Реализация подтверждается кодом, тестами и отчётом QA.

## 10. Открытые технические решения

До прототипа не фиксируются:
- REST/HTTP, локальный IPC, MCP, stdio или файловый транспорт;
- порт/endpoint;
- способ аутентификации и выдачи токенов;
- брокер сообщений и фоновые очереди;
- конкретная библиотека JSON Schema;
- модель запуска локально/серверно.

Критерий выбора — безопасное подключение нескольких независимых клиентов, работа в Windows, возможность автономного режима и поддерживаемость.

## 11. Минимальные тесты контракта

1. Корректный запрос и ответ валидируются по схеме.
2. Несовместимая версия отклоняется до запуска.
3. Запрос без разрешения на чтение не получает данные.
4. Агент не может вызвать инструмент, отсутствующий в available_tools.
5. Повторный idempotency key не дублирует действие.
6. Неоднозначный источник возвращает `needs_input` или `needs_review`, а не выдуманное значение.
7. Любое предложенное изменение содержит target и требует соответствующего разрешения.
8. Внешняя отправка/подписание/приёмка блокируются без явного подтверждения.
9. Ошибка адаптера не представляется как успешное выполнение.
10. Один и тот же агент работает через два разных тестовых адаптера без изменения ролевой спецификации.


## 12. Машинно-читаемые схемы версии 0.1

Логические структуры разделов 3–7 формализованы JSON Schema Draft 2020-12 в каталоге `contracts/schemas/`:

- `task-envelope.schema.json` — запрос клиента к агенту;
- `agent-response.schema.json` — ответ, доказательства, неопределённости, ошибки и предлагаемые действия;
- `artifact-manifest.schema.json` — описание артефакта, контрольная сумма и происхождение;
- `approval-record.schema.json` — решение человека по конкретному действию;
- `qa-report.schema.json` — независимый отчёт QA.

Индекс и правила использования: `contracts/README.md`.

Эти схемы являются первой формализованной редакцией 0.1. Они уточняют иллюстративные примеры выше, но не означают, что валидатор или runtime уже реализован. Перед производственным использованием необходимо:
1. проверить все файлы валидатором Draft 2020-12;
2. добавить положительные и отрицательные тестовые JSON-примеры;
3. проверить согласованность с версиями ролей и клиентских адаптеров;
4. зафиксировать правила публикации и неизменяемого разрешения URI схем;
5. согласовать любые несовместимые изменения через новую версию контракта.

Схема проверяет форму данных, но не заменяет проверку прав, подлинности источника, полномочий подписанта или достоверности инженерного содержания.

## 13. Бизнес-валидация и доверенный контекст

Помимо JSON Schema клиентский адаптер/runtime обязан запускать профильные бизнес-проверки до любого gate-перехода или внешнего действия. Прототип правил версии 0.1 описан в `contracts/BUSINESS_RULES_v0.1.md` и реализован в `scripts/agent_business_rules.py`.

Принципы:
- payload агента считается недоверенным, даже если он schema-valid;
- approval records, полномочия, статус ВОР в реестре, активность шаблона и разрешение на экспорт загружаются из доверенного хранилища;
- доверенный контекст формирует клиентский адаптер/сервер после аутентификации и авторизации; модель не вправе передавать его как собственное утверждение;
- отсутствие контекста, несовпадение ID/редакции или истёкшее разрешение блокирует операцию;
- утверждение ВОР, выпуск ИД, утверждение сметы, экспорт и принятие риска должны быть привязаны к аутентифицированному человеку с нужной ролью/полномочием; агент и технический сервис не могут выступать подписантом или владельцем принятого риска;
- бизнес-валидатор не выполняет операцию, а возвращает список нарушений; исполнительный компонент отдельно повторно проверяет разрешение непосредственно перед записью/экспортом.

Статусы и gate-переходы:
1. ВОР может перейти в `approved_by_gip` только при подтверждённой записи ГИПа, проверенных позициях, отсутствии открытых вопросов и блокирующих замечаний.
2. ИД может перейти в `released` только после проверки полей/приложений, сверки эталонного шаблона и отдельного решения уполномоченного лица.
3. Смета может перейти в `approved` только на утверждённой редакции ВОР, с сопоставленными нормами и отдельным утверждением сметчика.
4. Смета может быть передана в ГРАНД-Смета только при успешном обратном сравнении и отдельном разрешении `grand_smeta.export` на конкретную редакцию.
5. `QA_PASSED` и `CONDITIONAL_PASS` подчиняются независимости проверки, полноте обязательных проверок и правилам принятия рисков.

Unit-тесты подтверждают реализацию перечисленных правил на тестовых данных, но не заменяют интеграционную проверку реального хранилища полномочий, транзакционных переходов, блокировок и адаптеров.
