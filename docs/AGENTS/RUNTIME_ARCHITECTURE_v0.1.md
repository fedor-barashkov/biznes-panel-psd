# Архитектура исполняемой платформы строительных ИИ-агентов

**Версия:** 0.1  
**Дата:** 2026-11-10  
**Статус:** проектная архитектура MVP; реализация не начата.  
**Основание:** PLATFORM_SPEC_v0.1.md, ORCHESTRATOR_SPEC_v0.1.md, INTEGRATION_CONTRACT_v0.1.md, TRUST_BOUNDARY_SPEC_v0.1.md, контракты JSON Schema 0.1 и ролевые спецификации.

## 1. Архитектурное решение

Платформа строится как модульное локально-развёртываемое ядро с контрактными интерфейсами, а не как набор автономных чат-ботов и не как монолит, привязанный к приложению ИТД.

Логическая схема:

    Клиенты:
      приложение ИТД | ChatGPT/Codex/Claude | Excel/Word/PDF
      ГРАНД-Смета | другие строительные системы
                         |
                   Client Adapters
                         |
                  API / Local Gateway
                         |
       +---------------- Runtime Core ----------------+
       | Task Intake / Contract Validator             |
       | Identity / Policy Enforcement                |
       | Workflow Orchestrator / Execution Manager   |
       | Approval Manager / QA Gate                  |
       | Artifact & Revision Registry / Audit        |
       +----------------------------------------------+
             |                 |                 |
        Agent Runtime     Model Adapters     Tool Adapters
        ГИП / ПТО / QA     разные модели      документы и системы
             |
        Local Data Plane: задачи, артефакты, provenance,
        локальная очередь событий, аудит и резервные копии

Схема логическая: она не предписывает язык программирования, СУБД, протокол, поставщика модели или способ упаковки.

### 1.1. Основные решения

1. **Независимость от клиента.** Клиент обращается к платформе через версионируемый контракт и адаптер.
2. **Локальный режим — базовый.** MVP запускается на Windows-компьютере пользователя и выполняет локальные операции без обязательного постоянного подключения к серверу.
3. **Сервер — дополнительный контур.** Совместная работа и централизованное администрирование добавляются позднее без изменения базового контракта.
4. **Модели заменяемы.** Ролевая логика не зависит от конкретной модели; провайдер выбирается через Model Adapter и политику.
5. **Данные принадлежат клиенту.** Ядро не получает прямой доступ к внутренней БД клиента. Доступ — через ограниченные адаптеры.
6. **Никаких неявных полномочий.** Ответ модели не является разрешением на запись, выпуск, экспорт, подписание или приёмку.
7. **Артефакты версионируются.** Существенное изменение создаёт новую редакцию; утверждение относится только к конкретной редакции и действию.
8. **QA независим.** QA получает зафиксированную версию и критерии, не редактирует проверяемый результат и не утверждает его вместо человека.

## 2. Компоненты Runtime Core

| Компонент | Ответственность | Ограничение |
|---|---|---|
| API / Local Gateway | Приём запросов, клиентские сессии, маршрутизация | Не обходит политики |
| Task Intake | Контракт, схема, версия, обязательные поля, идемпотентность | Не принимает предметные решения |
| Identity Service | Установление субъекта и типа субъекта | Не признаёт агента человеком |
| PDP | Решение разрешить/запретить действие в scope | Сам не выполняет операцию |
| PEP | Принудительное применение решения перед защищённым действием | Не доверяет старому разрешению без перепроверки |
| PIP | Получение атрибутов субъекта, ресурса и контекста | Не расширяет scope |
| Workflow Orchestrator | Граф шагов, зависимости, условия переходов | Не выполняет инженерную работу |
| Agent Execution Manager | Запуск роли, лимиты, тайм-ауты, отмена и безопасные повторы | Не обходит ограничения роли |
| Agent Registry | Версии ролей, навыков, схем и совместимости | Не меняет утверждённую роль незаметно |
| Model Gateway | Интерфейс провайдеров, выбор модели, лимиты | Не передаёт модели неразрешённые данные |
| Tool Gateway | Каталог инструментов, схемы и проверка разрешений | Не даёт произвольный доступ к ОС/сети/БД |
| Approval Manager | Запрос, проверка и учёт решений человека | Не подписывает и не утверждает вместо человека |
| Artifact Registry | Метаданные, редакции, связи, provenance, хеши | Не переписывает историю |
| QA Gate | Независимая проверка и возврат на исправление | Не подменяет юридическую приёмку |
| Audit Store | Append-only журнал событий | Не допускает скрытого редактирования |
| Sync Manager (поздняя фаза) | Синхронизация событий и разрешение конфликтов | Не сливает конфликтующие утверждения автоматически |

Компоненты могут быть модулями одного процесса в MVP. Логическое разделение обязательно, микросервисная инфраструктура не требуется.

## 3. Границы доверия и потоки данных

### 3.1. Зоны доверия

- **Зона A — пользователь и клиент:** документы, подтверждения и пользовательские полномочия.
- **Зона B — Runtime Core:** контракты, маршрутизация, политика, версии, очередь и аудит.
- **Зона C — Agent/Model:** инструкции и модель. Ответ модели — недоверенное предложение до проверки схемой, бизнес-правилами и политикой.
- **Зона D — инструменты и внешние системы:** файловая система, БД клиента, офисные приложения, ГРАНД-Смета и сетевые API.
- **Зона E — сервер/синхронизация:** внешний контур, получающий только разрешённые данные.

### 3.2. Правила потока

1. Входной документ не может менять системные инструкции, права, маршрут или политику. Содержимое файла — недоверенные данные.
2. Агент получает только разрешённые для задачи документы и фрагменты.
3. Модель предлагает действие; Tool Gateway формирует проверяемый вызов; PEP повторно проверяет права непосредственно перед исполнением.
4. Существенные значения в ИД/ВОР/смете сохраняют связь с источником, редакцией и локатором.
5. Неподтверждённое значение не становится подтверждённым от повторения моделью или другим агентом.
6. Секреты и токены не передаются в промпт и не попадают в обычные логи.
7. Неизвестный результат внешней операции считается неоднозначным: сначала сверка состояния, затем продолжение.

### 3.3. Защита от prompt injection

- Разделять системные инструкции, пользовательское задание, извлечённое содержимое файлов и результаты инструментов.
- Помечать внешнее содержимое как недоверенные данные.
- Не предоставлять агенту неограниченный shell, произвольный HTTP или доступ ко всему диску.
- Каждый инструмент имеет входную/выходную схему, scope, разрешённые операции и лимиты.
- OCR сохраняет происхождение и уверенность; результат OCR не равен подтверждённому факту.

## 4. Жизненный цикл задачи

### 4.1. Состояния

    RECEIVED
      -> VALIDATING
      -> WAITING_FOR_INPUT | WAITING_FOR_PERMISSION | BLOCKED
      -> ROUTED -> RUNNING -> ARTIFACT_STAGED
      -> QA_PENDING
      -> QA_FAILED -> RUNNING (новая редакция)
      -> QA_PASSED
      -> WAITING_FOR_APPROVAL -> APPROVED
      -> RELEASE_PENDING -> COMPLETED

Дополнительные состояния: PARTIAL, FAILED, CANCELLED, EXPIRED, CONFLICTED. APPROVED и COMPLETED не взаимозаменяемы: утверждение — решение по конкретному действию и редакции; завершение — результат всего workflow.

### 4.2. Условия переходов

| Переход | Обязательное условие |
|---|---|
| RECEIVED → VALIDATING | Запрос принят, присвоен correlation ID |
| VALIDATING → ROUTED | Контракт, схема, версия и контекст валидны |
| VALIDATING → WAITING_FOR_INPUT | Недостаёт данных, которые нельзя безопасно вывести |
| VALIDATING → WAITING_FOR_PERMISSION | Не хватает разрешения |
| ROUTED → RUNNING | Роль, версия, инструменты и модель допущены политикой |
| RUNNING → ARTIFACT_STAGED | Ответ прошёл schema/business validation |
| ARTIFACT_STAGED → QA_PENDING | Зафиксирована неизменяемая версия |
| QA_PENDING → QA_FAILED | Есть блокирующие замечания или обязательные проверки не пройдены |
| QA_PENDING → QA_PASSED | Все обязательные проверки пройдены; Major обработаны по политике |
| QA_PASSED → WAITING_FOR_APPROVAL | Требуется человеческое решение |
| WAITING_FOR_APPROVAL → APPROVED | Подлинное решение проверено в точном scope |
| APPROVED → RELEASE_PENDING | Подготовлена отдельная операция выпуска/экспорта |
| RELEASE_PENDING → COMPLETED | PEP разрешил действие, адаптер подтвердил результат, аудит записан |
| Любое активное → FAILED | Неустранимая техническая ошибка |
| Любое активное → CANCELLED | Отмена разрешена и безопасна в текущей точке |

Ни модель, ни агент не могут самостоятельно переводить задачу в APPROVED, RELEASE_PENDING или COMPLETED.

### 4.3. Отмена и восстановление

- Отмена до внешнего действия прекращает новые шаги; уже созданные артефакты остаются в истории.
- Отмена во время внешней операции требует сверки фактического состояния.
- После аварийного завершения Runtime восстанавливает задачи по последнему подтверждённому событию и транзакционному состоянию.
- Неопределённые операции получают CONFLICTED/BLOCKED до сверки.

## 5. Маршрутизация и workflow

Маршрут выбирается по agent_id, task_type, зависимостям, входным данным и политике. Автоматический выбор разрешён только для заранее определённых типов задач. При неоднозначности платформа запрашивает уточнение, а не запускает все роли.

### 5.1. Анализ ПД/РД и ВОР

1. Intake фиксирует документы и редакции.
2. Навыки извлекают текст, таблицы, листы и локаторы.
3. ГИП анализирует комплект и готовит проект ВОР/замечаний.
4. Валидатор проверяет структуру, источники и происхождение расчётов.
5. QA независимо проверяет позиции, единицы, локаторы, конфликты и неопределённости.
6. Ответственный человек утверждает конкретную редакцию ВОР.
7. Сметчик получает только утверждённую редакцию, если сметный workflow разрешён.

### 5.2. Подготовка ИД

1. Intake определяет объект, подобъект, документ, шаблон и редакцию.
2. ПТО получает подтверждённые реквизиты и исходные сведения.
3. Агент готовит черновик, не создавая фактические даты, измерения, испытания или подписи.
4. QA проверяет шаблон, источники, комплектность, хронологию и приложения.
5. Человек проверяет и утверждает документ.
6. Выпуск/регистрация/передача выполняются отдельной операцией клиента после повторной проверки прав и версии.

### 5.3. Независимая проверка

QA получает зафиксированную редакцию только для чтения, критерии и контекст. Он возвращает findings, evidence и список непроверенного. Исправление создаёт новую редакцию; QA повторно проверяет её. Автор результата не закрывает собственные замечания.

### 5.4. Параллельность

Разрешена для независимых операций чтения, OCR, сравнения редакций и анализа независимых документов при изоляции контекстов. Запрещена для операций, зависящих от неутверждённого результата, конфликтующих записей и одновременного изменения одной редакции.

## 6. Артефакты, документы и версии

### 6.1. Модель хранения

Разделить:
- **метаданные:** ID, клиент, проект, объект/подобъект, тип, автор, время, состояние;
- **содержимое:** исходный файл, извлечённое представление, созданный артефакт;
- **provenance:** источник, редакция, локатор, метод извлечения, уверенность и проверка;
- **связи:** задача, роль, исходные документы, производные артефакты, QA, approval и экспорт;
- **контроль целостности:** SHA-256 или эквивалентный криптографический хеш;
- **аудит:** события жизненного цикла и действий.

### 6.2. Правила редакций

1. Исходные файлы неизменяемы; новая загрузка создаёт новую редакцию.
2. OCR и извлечённый текст — производные артефакты, связанные с исходником и версией инструмента.
3. Черновик агента не перезаписывает исходный документ.
4. Исправление создаёт новую редакцию; предыдущая остаётся в истории.
5. Approval относится к artifact_id + revision_id + action + scope + policy_version.
6. Изменение источника запускает impact analysis, но не переписывает утверждённые документы.
7. Экспорт формирует отдельный артефакт с манифестом, версией адаптера и round-trip результатом, если применимо.

### 6.3. Файловое хранилище

MVP использует локальное хранилище с разграничением метаданных и бинарных объектов. Путь к файлу не является разрешением. Доступ осуществляется через Artifact Service с проверкой scope и ACL. Нужны резервное копирование, проверка целостности и восстановление; удаление и retention регулируются явно.

## 7. Модели, навыки и инструменты

### 7.1. Model Gateway

Единый интерфейс поддерживает несколько провайдеров и локальные модели при технической возможности; маршрутизацию по сложности, цене, задержке и конфиденциальности; тайм-ауты, лимиты и параллельность; фиксацию model ID/version и параметров; обработку отказов; повторную оценку качества при смене модели. Если модель не соответствует профилю конфиденциальности проекта, запрос запрещается.

### 7.2. Skills

Skill — версионируемый модуль узкой компетенции с назначением, границами, входной/выходной схемой, необходимыми инструментами и правами, лимитами, обработкой ошибок, эталонными кейсами и регрессионными тестами.

Примеры: PDF/DOCX/XLSX extraction, OCR, таблицы, сравнение редакций, поиск реквизитов, проверка шаблона, provenance, генерация DOCX/PDF, экспорт/импорт сметных данных.

### 7.3. Tool Gateway

Инструмент не является произвольной функцией модели. Каталог содержит tool_id, версию, схему, допустимые роли, действия, scope, режим read/write/export, риск, необходимость approval и способ проверки результата. Каждый вызов получает уникальный operation ID и аудит.

## 8. Адаптеры клиентов и интеграции

| Адаптер | Назначение | Условия |
|---|---|---|
| ITD Desktop Adapter | Карточки объекта, документы, шаблоны и разрешённые действия | Версия контракта, объектный scope, проверка прав |
| AI Client Adapter | Задачи от ChatGPT/Codex/Claude | Явное подключение инструментов; без прямого доступа к БД ИТД |
| Office/File Adapter | PDF, DOCX, XLSX и изображения | Проверка типа, размера, безопасности и provenance |
| Excel Автогенератор Adapter | Совместимость с книгами и шаблонами | Аудит формул, макросов и формата обмена |
| Grand Smeta Adapter | Импорт/экспорт сметных данных | Отдельное разрешение; round-trip кодов, шифров, названий, единиц, количеств и коэффициентов |
| Other Client Adapter | Новые строительные приложения | Общий контракт и сертификационные тесты |

Адаптеры независимы. Сбой адаптера не разрушает состояние ядра; операция получает явную ошибку или статус неопределённого результата.

## 9. Локальный Windows и автономный режим

### 9.1. Целевой режим MVP

- Локальный запуск на Windows x64; минимальная версия ОС определяется техническим spike.
- Один компьютер пользователя — один локальный runtime и локальное хранилище с корректными ACL.
- Просмотр сохранённых задач/артефактов и локальные операции доступны без сети.
- Схемы, бизнес-правила, аудит и локальные workflow работают офлайн.
- Облачные модели требуют сети и разрешения на передачу соответствующего контекста.
- При недоступности провайдера задача ожидает подключения или переключается на разрешённую локальную модель; ложный успех запрещён.
- Обновление не меняет данные без миграционного плана и резервной копии.

Offline-first не означает, что любая модель или интеграция работает без интернета. Это означает, что локальные данные, документы, состояние задач, аудит и доступные локальные операции сохраняют работоспособность, а сетевые зависимости изолированы.

### 9.2. Синхронизация — следующая фаза

Синхронизируются события и версии, а не «последняя копия всего» без контроля. Нужны уникальные идентификаторы, идемпотентность, причинно-следственные связи, защита от replay, ручное разрешение конфликтов, шифрование и повторная проверка прав на сервере. Конфликтующие утверждённые документы автоматически не объединяются.

## 10. Безопасность, согласования и аудит

Runtime реализует TRUST_BOUNDARY_SPEC_v0.1.md. Минимальный защищённый контур:
1. аутентификация локального пользователя и установление actor type;
2. PDP выдаёт решение в scope конкретного действия;
3. PEP повторно проверяет решение перед исполнением;
4. approval/permit ограничен субъектом, ресурсом, редакцией, действием, сроком и nonce;
5. изменение версии ресурса аннулирует старое разрешение;
6. операции записи атомарны с проверкой версии;
7. журнал append-only для обычных пользователей и агентов;
8. ошибка аудита при защищённой операции приводит к отказу;
9. агент/модель не может стать human principal;
10. секреты хранятся в защищённом хранилище ОС/провайдера.

До выбора и проверки локальной идентичности, защищённого хранения секретов, криптографической проверки разрешений и транзакционного аудита runtime работает только в read-only/draft режиме. Write/export не включаются до прохождения соответствующих испытаний.

## 11. Наблюдаемость и эксплуатация

Для каждой задачи доступны timeline состояний и действий; request/task/correlation/operation IDs; версии ролей, навыков, моделей и адаптеров; входные/выходные артефакты; источники и локаторы; решения PDP/PEP и approval; QA findings и исправления; время/стоимость вызовов (если доступны); ошибки, retry и причины блокировки.

Логи не содержат пароли, токены и неограниченные фрагменты конфиденциальных документов. Интерфейс показывает частичный результат, ожидание, блокировку, непроверенные элементы и причину отказа, а не только «успех».

## 12. Развёртывание, обновления и резервное копирование

MVP: локальный Windows runtime как отдельный сервис/процесс, управляемый клиентом; API/Local Gateway обслуживает ИТД и другие адаптеры; пакет установки проверяет подпись, версию и целостность; конфигурация отделена от бинарных файлов; миграции выполняются после резервного копирования; предусмотрены журнал версий и откат; диагностический пакет исключает секреты и избыточные персональные данные.

Открыто решение, поставлять runtime отдельным установщиком или комплектом с ИТД. Архитектурно предпочтительно отдельное ядро с независимым жизненным циклом и версионируемым API.

## 13. Объём MVP и этапы

### MVP-0 — безопасное локальное ядро (без внешней записи)

- локальный запуск и конфигурация;
- API/Local Gateway;
- Task Intake и валидация контрактов;
- Agent Registry и версии;
- маршрутизация на одну роль за задачу;
- Model Gateway с одним провайдером и интерфейсом расширения;
- Artifact Registry, версии и provenance;
- локальное файловое хранилище;
- состояния задач и восстановление после перезапуска;
- базовый аудит;
- read-only/draft tools;
- тестовый клиент и диагностический harness.

### MVP-1 — контролируемый workflow

- workflow ГИП/ПТО/QA;
- независимый QA Gate;
- human approval flow;
- PDP/PEP/PIP и локальная идентичность;
- транзакционный аудит, nonce/replay и optimistic concurrency;
- права на уровне клиента/проекта/объекта/подобъекта/артефакта;
- безопасные retry и отмена;
- тесты prompt injection и изоляции клиентов.

### MVP-2 — первые реальные адаптеры

- адаптер приложения ИТД;
- Office/File Adapter для PDF/DOCX/XLSX;
- интеграционный тест с Excel Автогенератором;
- тестовый обмен с ГРАНД-Смета в отдельном контуре без производственной записи;
- round-trip проверка и манифесты экспорта.

### MVP-3 — совместная работа и расширение

- серверный runtime и синхронизация;
- несколько пользователей и организаций;
- удалённые адаптеры;
- дополнительные и локальные модели;
- управление политиками, телеметрия и централизованное обновление.

**Не входит в первый MVP:** автоматическое подписание/приёмка; самостоятельный выпуск юридически значимых документов; автономное создание фактов выполнения работ; бесконтрольная запись в ГРАНД-Смета; произвольный доступ агента к компьютеру; обязательная облачная зависимость; микросервисная инфраструктура.

## 14. Критерии приёмки MVP

MVP-0 не принимается без:
1. локального запуска на чистой поддерживаемой Windows-среде;
2. восстановления после перезагрузки и аварийного завершения;
3. проверки схем до запуска агента;
4. выбора маршрута и отказа при неизвестном/неразрешённом task type;
5. идемпотентности повторного запроса;
6. фиксации артефакта, версии, хеша и provenance;
7. разделения draft, QA и approval статусов;
8. отсутствия внешней записи и выпуска в MVP-0;
9. журналирования переходов и ошибок без секретов;
10. работы локальных функций без сети и корректного ожидания облачной модели;
11. резервного копирования и успешного восстановления;
12. автоматизированных тестов отказов, повреждённого файла, повторного запроса и перезапуска.

MVP-1 дополнительно не принимается без тестов human-only approval, separation of duties, PDP/PEP для каждой write/export операции, replay/version conflict, независимости QA, scope на клиент/проект/объект/подобъект и append-only аудита с проверкой целостности.

Каждый критерий получает статус NOT_RUN, PASS, FAIL или BLOCKED, ссылку на доказательство и версию сборки. Отсутствие теста не считается PASS.

## 15. План технических исследований до выбора стека

1. Windows service/process lifecycle, права, обновление и запуск без администратора.
2. Локальный IPC/API и безопасная привязка к пользователю/процессу.
3. Хранилище метаданных, транзакции, блокировки, резервное копирование и восстановление.
4. Защищённое хранение ключей/секретов и проверка подписи permit.
5. PDF/DOCX/XLSX/OCR на реальных образцах и требования к приватности.
6. Model Gateway: облачная и локальная модель, сетевые сбои, политика передачи данных.
7. Совместимость API и контрактов с несколькими клиентами.
8. Упаковка, подпись, обновление и откат Windows runtime.

Каждый spike завершается ADR с измерениями, рисками, альтернативами и тестовым доказательством. До завершения spike конкретный стек не утверждается.

## 16. Открытые решения

До соответствующей фазы необходимо определить: отдельный установщик или поставка с ИТД; локальный транспорт и идентификация клиента; СУБД/структура файлов; разрешённые модели для классов документов; профиль Windows и системные требования; механизм подписи approval/permit; сроки хранения и удаления; реальные интерфейсы ГРАНД-Смета 2026 и Автогенератора; операции, допустимые офлайн, и правила разрешения конфликтов.
