# Архитектурное решение ADR-001: рекомендуемый технологический стек

**Версия:** 0.2  
**Статус:** .NET/WPF — ведущая рекомендация и кандидат для технического spike; окончательное решение принимается только по результатам испытаний, определённых в ТЕХНИЧЕСКИЙ_SPIKE_v0.1.md.  
**Дата проверки платформ:** 2026-11-08.

## 1. Контекст

Целевой продукт — самостоятельное Windows-приложение ИТД с локальной автономной работой, сложными рабочими областями документов, реестрами, импортом/распознаванием, печатью, редактором исполнительных схем, хранением оригиналов и дальнейшим сетевым режимом.

Статический аудит показал, что текущий `biznes-panel-psd` — монолитный HTML/CSS/JavaScript-файл без сборочной системы и собственной транзакционной БД; локальные данные хранятся в `localStorage`, а облачные функции зависят от API Claude. Ветка `main` не содержит Windows-проекта, установщика или тестовой инфраструктуры.

Следовательно, простое переименование/упаковка текущего HTML в EXE не обеспечивает требования по данным, версиям, архиву, резервированию, автономной работе и сетевой синхронизации. Существующий код сохраняется как источник функциональных решений и UX-референс; повторное использование отдельных частей определяется по результатам проверки.

## 2. Рассмотренные варианты

| Критерий | .NET 10 + WPF | Tauri 2 + web UI | Electron |
|---|---|---|---|
| Ориентация на Windows desktop | Нативная Windows-only платформа | Desktop-оболочка с WebView2 | Desktop-оболочка с Chromium/Node |
| Повторное использование HTML/CSS | Низкое/среднее | Высокое | Высокое |
| Сложные рабочие области, таблицы, дерево, вкладки, команды | Сильная встроенная база WPF | Реализуется web UI | Реализуется web UI |
| Интеграция с Windows и печатью | Прямой .NET API | Через Rust-плагины/команды | Через Node/Electron API |
| Локальная БД и файловые операции | Прямые .NET библиотеки | Через Rust/plugins | Через Node и native modules |
| Требования к сборочной среде | .NET SDK/Windows tooling | Rust, C++ Build Tools, WebView2 | Node.js и инструменты упаковки |
| Риск избыточной сложности | Средний | Средний/высокий: два языка и мост UI/backend | Средний/высокий: Chromium runtime и Node surface |
| Соответствие Windows-only продукту | Высокое | Высокое | Высокое |

## 3. Рекомендуемое решение

**Рекомендуется .NET 10 LTS + WPF + C# для самостоятельного Windows-приложения ИТД.**

Обоснование:
- продукт целится в Windows и не обязан быть кроссплатформенным;
- WPF предоставляет настольную модель окон, страниц, вкладок, контекстных команд, таблиц, дерева, форм, просмотра документов и 2D-графики;
- WPF поддерживает data binding, команды, стили и шаблоны элементов, что соответствует требованию динамической ленты и рабочих областей;
- приложение не будет зависеть от браузерного хранилища, API Claude, CDN и установленного браузера;
- доменную логику можно отделить от интерфейса и использовать её в локальном режиме и будущем серверном API.

WPF является Windows-only технологией. Это соответствует текущей целевой платформе, но исключает прямой перенос GUI на macOS/Linux без отдельного клиента.

## 4. Предлагаемая структура решения ИТД

### 4.1. Клиент

- C# / .NET 10 LTS;
- WPF, MVVM;
- модульный монолит на первом этапе: единое устанавливаемое приложение, разделённое на доменные модули и слои;
- локальная конфигурация и фоновые задачи;
- отсутствие обязательной зависимости от интернета и облачного ИИ.

Не дробить приложение на микросервисы в локальном релизе. Разделение выполнять на уровне модулей и контрактов.

### 4.2. Данные и файлы

- Локальная транзакционная БД: SQLite.
- Серверная БД для будущего сетевого этапа: PostgreSQL.
- Файлы — отдельное управляемое хранилище с неизменяемыми оригиналами, редакциями, хешами и метаданными.
- В БД хранятся метаданные, связи, версии, provenance, права, события и индексы; бинарные файлы не следует хранить как неструктурированные большие поля без обоснования.
- Миграции схемы БД версионируются.
- Резервная копия включает БД, файлы, связи, историю, шаблоны и настройки.

SQLite и PostgreSQL требуют отдельной проверки совместимости SQL, типов и транзакций. Не допускать зависимости бизнес-логики от специфических возможностей только одной СУБД без адаптера.

### 4.3. Серверный этап

- ASP.NET Core API;
- PostgreSQL;
- централизованное файловое хранилище;
- авторизация, аудит, мониторинг и резервирование;
- локальная очередь изменений и контролируемая синхронизация.

Сетевой этап не реализуется до устойчивого локального цикла, но интерфейсы репозиториев, транзакционные границы и модель версий должны быть подготовлены заранее.

### 4.4. Документы и интеграции

Для Word/Excel/PDF, OCR, печати и схем создать отдельные адаптеры. Конкретные библиотеки выбираются только после коротких прототипов на реальных пользовательских образцах и проверки лицензий. Не обещать сохранение сложного оформления Word/Excel до тестирования конкретных шаблонов.

### 4.5. Агентная платформа

Платформа агентов остаётся в отдельном репозитории `construction-ai-agents`. Она не входит в WPF-процесс и не получает прямой доступ к БД ИТД. Связь — через версионируемый контракт и клиентский адаптер. Для разных ИИ-провайдеров и приложений используются отдельные адаптеры.

Реализационный язык/рантайм платформы агентов выбирается отдельно; не смешивать его с выбором стека приложения ИТД.

## 5. Почему не рекомендованы простая упаковка HTML и Electron как основной вариант

### Упаковка существующего HTML

Не решает проблемы `localStorage`, Claude API, отсутствия транзакционной БД, файлового хранилища, редакций, синхронизации и тестовой инфраструктуры. Может быть использована только как временный демонстрационный прототип, не как архитектура продукта.

### Tauri 2

Хороший вариант, если приоритетом станет повторное использование HTML/CSS. Однако на Windows разработка требует Rust, Microsoft C++ Build Tools и WebView2; логика приложения будет разделена между web UI и native backend. Это допустимо, но увеличивает число технологических границ, которые нужно сопровождать.

### Electron

Поддерживает упаковку веб-приложений в desktop-дистрибутив, но для данного Windows-only продукта добавляет Chromium/Node runtime и дополнительную поверхность сопровождения. В текущем случае преимущества кроссплатформенного web UI не перевешивают нативную интеграцию WPF.

## 6. Условия до утверждения

До начала прикладной реализации выполнить короткий технический spike:
1. создать пустой WPF-проект на .NET 10;
2. проверить автономную сборку и запуск на чистой Windows-системе;
3. проверить SQLite, миграцию схемы и транзакции;
4. проверить открытие/сохранение тестовых файлов и печать;
5. проверить табличный реестр, контекстную ленту и отдельную рабочую область документа;
6. проверить рендеринг пользовательского АОСР.docx, Реестр ИД.xlsx и PDF-образцов из полученного архива;
7. оценить редактор векторной исполнительной схемы;
8. проверить тестирование и сборку через GitHub Actions Windows runner.

Если spike выявит критическое ограничение, ADR пересматривается до разработки основного функционала.

## 7. Критерии принятия решения

Рекомендация принимается, если пользователь согласен с:
- Windows-only GUI на WPF;
- .NET 10 LTS как базовой платформой;
- локальной SQLite на первом этапе;
- PostgreSQL + ASP.NET Core как целевым сетевым контуром;
- отдельной независимой платформой агентов с собственным стеком;
- сохранением старого HTML как источника функциональных решений, но не как готовой архитектуры продукта.

## 8. Уточнение по существующим исходникам пользователя

Проведён первичный статический аудит репозитория manager-executive-schemes. В нём уже есть WPF/C#/SQLite приложение, которое может дать проверенные паттерны для локальной БД, карточек объектов и работы с Visio. Однако его текущий TargetFramework — net8.0-windows, а поддержка .NET 8 заканчивается 10 ноября 2026 года. Новый продукт не должен наследовать эту целевую платформу без обновления.

В spike необходимо сравнить:
- новый чистый каркас WPF на .NET 10;
- перенос выбранных компонентов manager-executive-schemes на .NET 10;
- альтернативный Tauri 2 прототип.

Репозиторий itd.html даёт полезный UX и словарь сущностей, но использует React/TypeScript и localStorage; его хранилище не подходит как целевая модель данных. Подробности и ограничения зафиксированы в АУДИТ_СУЩЕСТВУЮЩИХ_GITHUB_ПРОЕКТОВ_v0.1.md.

## 9. Официальные источники

- Microsoft: [.NET Support Policy](https://dotnet.microsoft.com/en-us/platform/support/policy) — .NET 10 обозначен как LTS с активной поддержкой до 14 ноября 2028 года (состояние источника на 25 октября 2026).
- Microsoft: [WPF overview](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview) — WPF является Windows-only UI framework и включает data binding, controls, layout, graphics, documents и printing-related controls.
- Tauri: [Windows prerequisites](https://tauri.app/start/prerequisites/) — для Windows требуются Microsoft C++ Build Tools и WebView2; Tauri также требует Rust.
- Electron: [Application packaging](https://www.electronjs.org/docs/latest/tutorial/application-distribution) — для распространения приложения его необходимо упаковать и подготовить дистрибутив; документация рекомендует специализированные инструменты, например Electron Forge.

## 9. Статус

Это техническая рекомендация, а не утверждённый стек. Код проекта не изменялся. После принципиального утверждения выполняется технический spike, затем фиксируется окончательный ADR с результатами фактических испытаний.

## Дополнение: ограничения совместимости, выявленные аудитом 2026-11-08

Статический аудит архива `agenerator_5.26.10.09_(1).zip` подтвердил, что исходная автоматизация использует Excel/Power Query/VBA и автоматизацию Word, а ОЖР использует отдельную XLSM-книгу и Power Query для чтения файлов из папки. В комплекте доступны шаблоны АОСР, других актов, реестра ИД и приложений. Быстрый старт требует Excel/Office и изменения настроек активного содержимого и конфиденциальности Power Query; такие требования не переносить в ИТД. Это не основание переносить Office как обязательный runtime новой ИТД.

Требования к технологическому решению:
1. Чтение XLSX/XLSM — через безопасный OOXML-парсер; VBA не исполнять.
2. Генерация DOCX — через библиотеку, сохраняющую структуру и форматирование шаблона; решение подтвердить сравнением эталонных рендеров.
3. Генерация PDF/печати не должна требовать установленного Microsoft Office, если это не является отдельно утверждённым ограничением.
4. Power Query M использовать как документацию/контрольный источник алгоритмов, а не как обязательную среду исполнения.
5. Сетевые API, Google Sheets и лицензионные механизмы исходного продукта не переносить в ядро.
6. Хранение секретов — вне исходного кода, с минимальными правами и возможностью ротации.
7. Не требовать от пользователя отключать глобальные механизмы безопасности Office, разрешать макросы или запускать EXE/BAT из импортируемых архивов.
8. В Power Query исходной книги обнаружен параметр с 64-символьным hex-значением, используемый в API-сценарии графика. Значение не переносить и не публиковать; владельцу исходного сервиса проверить его статус и при необходимости выполнить ротацию.

Рекомендация .NET 10 LTS + C# + WPF/MVVM + SQLite остаётся предложением. Аудит исходников не означает её утверждения. Окончательный выбор должен учитывать возможности выбранных библиотек для точного DOCX/PDF-рендеринга, офлайн-режима, обновлений и целевой Windows-среды.
