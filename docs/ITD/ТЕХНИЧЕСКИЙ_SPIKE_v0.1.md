# Технический spike приложения ИТД

**Версия:** 0.1  
**Дата:** 2026-11-08  
**Статус:** план испытаний; технологический выбор не сделан.  
**Связанные документы:** ADR-001-Технологический_стек.md; СТРАТЕГИЯ_ПЕРЕНОСА_АВТОГЕНЕРАТОРА_И_ПЛАН_РЕАЛИЗАЦИИ_v1.0.md; АУДИТ_АВТОГЕНЕРАТОРА_5.26.10.09.md.

## 1. Цель

На реальных файлах проекта проверить, какой Windows desktop стек способен обеспечить надёжную локальную ИТД, точное заполнение пользовательских DOCX/XLSX, воспроизводимую печать, безопасный импорт, резервирование и последующее сопровождение.

Spike не является началом полноценной реализации и не должен превращаться в демонстрационный макет. Его результат — измеримые доказательства выбора технологии, проверяемый прототип технических операций, перечень ограничений и обновлённый ADR-001.

## 2. Кандидаты

Основные кандидаты:
- .NET 10 LTS + C# + WPF как новый чистый каркас;
- перенос применимых частей существующего manager-executive-schemes с net8.0-windows на .NET 10 LTS как отдельная ветка испытания;
- Tauri 2 + TypeScript/web UI + Rust backend.

Существующий manager-executive-schemes — реальный WPF/SQLite проект, но он узкоспециализирован на Visio и не является готовым приложением ИТД. Его следует рассматривать как исходник отдельных паттернов и компонентов, а не автоматически брать целиком за основу. Статический аудит зафиксирован в АУДИТ_СУЩЕСТВУЮЩИХ_GITHUB_ПРОЕКТОВ_v0.1.md.

Electron рассматривается только как контрольный вариант, если выяснится, что перенос существующего web UI существенно сокращает сроки без неприемлемого роста размера, поверхности атаки и сложности сопровождения.

Не добавлять новые кандидаты без конкретной причины. Для всех вариантов используется один и тот же набор тестовых файлов, сценариев и критериев.

## 3. Контрольный набор исходных материалов

Минимальный набор:
1. Пользовательский шаблон АОСР.docx — главный тест сохранения DOCX-структуры и форматирования.
2. Реестр ИД.xlsx — проверка точности табличной печатной формы.
3. ОЖР_5.3.8.xlsm — только безопасный статический импорт/инвентаризация без запуска VBA.
4. PDF «Быстрый старт» — проверка извлечения текста и страниц.
5. Набор DOCX иных актов — проверка многостраничных таблиц, подписей, приложений и разрывов страниц.
6. Несколько изображений/сканов и PDF с текстовым слоем — OCR и различение распознанного/подтверждённого значения.
7. Контрольный искусственный объект с несколькими подобъектами, организациями, представителями, работами, материалами, партиями, актами и приложениями.

Оригиналы тестовых файлов не изменять. Для каждого файла зафиксировать SHA-256, размер, формат и роль в испытании. Конфиденциальные или реальные персональные данные не использовать без необходимости.

## 4. Обязательные испытания

| ID | Испытание | Измеримый результат | Условие прохождения |
|---|---|---|---|
| SPIKE-01 | Чистая сборка приложения | Команды сборки, версии SDK/toolchain, результат и лог | Сборка воспроизводима по инструкции на чистой Windows VM/ПК |
| SPIKE-02 | Локальная БД | Создание, CRUD, транзакции, уникальные ограничения, миграции | Нет потери/дублирования данных; откат транзакции корректен |
| SPIKE-03 | Резервирование | Backup, восстановление в отдельную папку/БД, проверка целостности | Восстановленная БД и файлы совпадают по контрольным данным и хешам |
| SPIKE-04 | Импорт файлов | DOCX/XLSX/XLSM/PDF/PNG/JPG | Оригинал сохранён побайтно; импорт не исполняет макросы/скрипты |
| SPIKE-05 | Заполнение АОСР | Заполнить контрольный документ по тестовым данным | Не разрушены таблицы, стили, секции, поля, подписи и приложения |
| SPIKE-06 | Генерация PDF | DOCX → PDF на целевой Windows-среде | Не меняется геометрия страниц; переносы и подписи сверены визуально |
| SPIKE-07 | Реестр ИД | Заполнение эталонного XLSX или его точного воспроизведения | Графы, порядок, размеры, блоки «Сдал/Принял» соответствуют образцу |
| SPIKE-08 | Provenance | Просмотр источника каждого распознанного поля | Для каждого поля доступен файл и точный локатор источника, метод и подтверждение |
| SPIKE-09 | Офлайн | Отключить сеть и повторить основные операции | Создание/редактирование/печать/поиск/backup работают без сети |
| SPIKE-10 | Установка и запуск | Установка на чистую поддерживаемую Windows | Нет ручной установки Office/Excel как обязательного условия; приложение запускается без dev-инструментов |
| SPIKE-11 | Обновление | Установить следующую сборку поверх предыдущей | Пользовательские данные и файлы сохранены; миграция обратима или предусмотрен безопасный recovery |
| SPIKE-12 | Производительность | Импорт и поиск на согласованном контрольном наборе | Время и память измерены; нет зависания UI при длительных операциях |
| SPIKE-13 | Права и аудит | Действия пользователя без разрешения и с разрешением | Запрещённое действие блокируется; событие аудита сохраняет актор/время/объект/результат |
| SPIKE-14 | Печатная регрессия | Сравнение PDF с утверждёнными golden masters | Все расхождения классифицированы; критические визуальные отличия отсутствуют |
| SPIKE-15 | Перенос существующей WPF-основы | Сборка manager-executive-schemes после обновления target framework до net10.0-windows и проверка его SQLite/Visio-функций | Сборка проходит; миграции БД и COM-сценарии работают на Windows; выявленные несовместимости задокументированы |

## 5. Визуальная проверка DOCX/PDF

Для АОСР и реестра ИД необходимо сравнивать:
- размер и ориентацию страницы;
- поля и область печати;
- ширину столбцов и высоту строк;
- шрифты, кегли, начертания и межстрочные интервалы;
- границы и объединения ячеек;
- разрывы страниц и переносы таблиц;
- колонтитулы, номера страниц и подписи;
- порядок приложений и отсутствие обрезанных строк.

Сравнение должно включать автоматическую проверку количества страниц и растровое наложение/визуальный diff. Любое допустимое расхождение документируется. Простого утверждения «файл открылся» недостаточно.

## 6. Правила тестовой реализации

- Для каждого кандидата реализуется одинаковый минимальный набор технических операций, без разработки полноценного пользовательского интерфейса.
- Используется один и тот же тестовый набор и одинаковые сценарии.
- Не подключать внешние API и ИИ; испытания должны воспроизводиться офлайн.
- Не запускать VBA и макросы из XLSM.
- Не изменять оригинальные шаблоны; результат сохранять в отдельную папку.
- Библиотеки генерации DOCX/PDF выбираются только после теста реальных файлов, проверки лицензий, поддержки и ограничений.
- Любые секреты и токены запрещено включать в репозиторий и тестовые данные.

## 7. Матрица оценки

После прохождения обязательных ворот кандидаты оцениваются по 100-балльной шкале:

| Критерий | Вес |
|---|---:|
| Точность DOCX/PDF и печатных форм | 25 |
| Целостность БД, транзакции, backup/restore | 20 |
| Автономность и стабильность Windows desktop | 15 |
| Безопасность импорта и минимальность attack surface | 10 |
| Простота сопровождения и доступность специалистов | 10 |
| Воспроизводимость сборки, установки и обновления | 10 |
| Производительность и отзывчивость UI | 5 |
| Возможность будущего сетевого режима без переписывания домена | 5 |
| **Итого** | **100** |

Кандидат не может быть выбран только по сумме баллов, если он провалил обязательное испытание SPIKE-02, SPIKE-03, SPIKE-05, SPIKE-06, SPIKE-09 или SPIKE-10.

Рекомендуемый порог — 80/100 при отсутствии провалов обязательных ворот. Если ни один кандидат не проходит порог, корректируется техническое решение или библиотечный набор и повторяются неудачные тесты.

## 8. Требуемые артефакты результата

1. Репозиторий/ветка spike с минимальными исходниками и инструкцией запуска.
2. Зафиксированные версии SDK, библиотек и лицензии.
3. Скрипт подготовки тестовых данных и список хешей исходников.
4. Логи сборки, тестов, backup/restore и измерений.
5. PDF и изображения результатов печати для сравнения.
6. Таблица оценки кандидатов с доказательствами по каждому критерию.
7. Список технических рисков и ограничений.
8. Обновлённый ADR-001 с выбранным стеком и обоснованием либо с объяснением, почему выбор пока невозможен.

## 9. Ограничения текущего исполнения

Статический анализ архива и выбранных файлов существующих GitHub-проектов уже выполнен. Макросы и EXE/BAT не запускались. Существующий manager-executive-schemes использует .NET 8; по официальной политике Microsoft поддержка .NET 8 заканчивается 10 ноября 2026 года, поэтому новый продукт не должен целиться в net8.0. Для нового продукта ориентир — .NET 10 LTS, поддерживаемый до 14 ноября 2028 года. Источник: https://dotnet.microsoft.com/en-us/platform/support/policy. Для достоверного испытания установки, печати и поведения на чистой Windows требуется запуск на Windows-среде. Если текущая среда разработки не предоставляет такую машину, spike-код и воспроизводимые команды готовятся в репозитории, а Windows-прогоны выполняются в Windows CI или на компьютере пользователя; неподтверждённые результаты не объявляются пройденными.

## 10. Критерий завершения spike

Spike завершён только после получения всех артефактов раздела 8, прохождения обязательных ворот, заполнения матрицы оценки и документированного решения по ADR-001. До этого .NET/WPF остаётся ведущей рекомендацией, но не утверждённым фактом.
