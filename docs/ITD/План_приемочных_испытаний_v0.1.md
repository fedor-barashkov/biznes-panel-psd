# План приёмочных испытаний приложения ИТД

**Версия:** 0.1  
**Основание:** `docs/ITD/Техническое_задание.md` v0.6, `docs/ITD/Архитектура.md`, `docs/ITD/Регламенты.md`.  
**Статус:** план подготовлен; испытания не выполнялись.  
**Правило:** тест считается пройденным только после фактического выполнения на собранном приложении с сохранением доказательств.

## 1. Назначение и правила

План определяет минимальный набор сквозных проверок для локального релиза Windows. Он дополняется тестами отдельных модулей и регрессией. Проверки выполняются на тестовых данных; реальные документы и персональные данные без необходимости не использовать.

Статусы:
- `NOT_RUN` — не выполнялся;
- `PASS` — фактически пройден;
- `FAIL` — фактически не пройден;
- `BLOCKED` — невозможно выполнить из-за зависимости;
- `NOT_VERIFIED` — нет достаточных доказательств.

Критичность:
- **Blocker** — потеря/повреждение данных, нарушение статуса приёмки, подмена оригинала, несанкционированное действие, невозможность основного сценария;
- **Critical** — неверная форма/реквизит/связь, нарушение целостности комплекта или существенная ошибка документа;
- **Major** — важная функция работает неверно, но есть обходной путь;
- **Minor** — косметическая или несущественная проблема.

## 2. Предрелизные условия

Перед испытаниями зафиксировать:
- версию приложения и commit;
- Windows edition/build и разрядность;
- версии .NET/runtime или иных необходимых компонентов после выбора стека;
- версию схемы БД и миграций;
- версии шаблонов и нормативных справочников;
- конфигурацию локального хранилища и резервирования;
- тестовые организации, объект, подобъекты и документы;
- состав разрешений тестовых пользователей;
- способ получения логов и диагностических сведений.

| ITD-004 | Карточка объекта и исходно-разрешительные документы | Реквизиты разрешения на строительство и заключения экспертизы сохраняются с источником, датой и историей; изменения не переписывают ранее выпущенные документы |

| ITD-008 | Происхождение данных (provenance) | Для значимых полей доступен источник: файл, версия, страница/лист/ячейка, способ извлечения, дата и подтвердивший пользователь |

| ITD-010 | Создание АОСР | Рабочая область соответствует утверждённой компоновке; поля, порядок, формулировки, подписи и приложения соответствуют пользовательскому шаблону и применимой форме |
| ITD-011 | Дата акта и хронология | Дата акта по умолчанию равна дате окончания работ; система не подменяет фактические даты и не исправляет их без подтверждения |
| ITD-012 | Выпуск с незаполненными обязательными полями | Перед выпуском показан перечень пропусков; только уполномоченный пользователь может выпустить с явной отметкой; последующее заполнение отражается в истории |
| ITD-013 | Шаблоны и редакции | Документ хранит точную редакцию шаблона; изменение шаблона не меняет старые документы; опубликованная редакция защищена от прямого редактирования |
| ITD-014 | Шаблоны заказчиков Word/Excel | Структура и оформление исходного шаблона сохраняются в пределах возможностей формата; оригинал не перезаписывается; результат доступен для проверки |
| ITD-015 | Предварительный просмотр и печать | Каждый документ перед выпуском можно просмотреть в итоговом виде; печать из preview не выпускает документ и не меняет статус |
| ITD-016 | Исполнительная схема | Можно создать с нуля, на подложке и из готового файла; оригинал сохраняется; поддерживаются листы/форматы/связь с АОСР; печать и PDF соответствуют выбранному шаблону |
| ITD-017 | Материалы, партии и документы качества | Количественный расход связан с партиями и остатками; один документ качества не дублируется; автоподбор предлагает кандидатов, но пользователь подтверждает соответствие |
| ITD-018 | Протоколы испытаний | Значения и результаты извлекаются только из источника; связи с материалами/партиями/актами подтверждаются; протокол не создаёт фиктивных результатов |
| ITD-019 | ОЖР и специальные журналы | Используются применимые нормативные редакции; старый журнал сохраняет исходную форму; записи из АОСР переносятся только в предусмотренные поля; хронология проверяется без скрытого исправления |
| ITD-020 | Реестр ИД | Записи формируются из документов и подтверждённых связей без дублей; внутренние статусы видны в электронном реестре; печатный реестр не содержит внутренних статусов и соответствует эталону |
| ITD-021 | Связи документов | Проверены связи 1:1, 1:N, N:1, N:M; кратность и обязательность применяются; разрыв связи не удаляет исходные документы |
| ITD-022 | Изменение исходного документа | Система находит зависимые документы и предлагает проверку; не меняет и не выпускает их автоматически |
| ITD-023 | Комплектование и передача | Формируется полный комплект выбранной области; снимок фиксирует состав, версии, файлы и хеши; повторная передача не меняет прошлую |
| ITD-024 | Приёмка документов | До явного подтверждения статус «Не принят»; статус меняется только уполномоченным лицом; частичная приёмка фиксируется по каждому документу; таймер не меняет статус |
| ITD-025 | Подтверждение фактической передачи | Описи, акты передачи и протоколы связаны с конкретным событием; загрузка файла сама по себе не означает приёмку |
| ITD-026 | Права и аудит | Базовые роли и индивидуальные права работают по объектам/подобъектам; запрещённые действия отклоняются; журнал аудита защищён от обычного изменения |
| ITD-027 | Архив и восстановление | Оригиналы, редакции, архив и корзина работают по категориям защиты; восстановление сохраняет историю и связи |
| ITD-028 | Резервная копия | В копию входят БД, файлы, версии, связи, история, настройки, права и шаблоны; контрольная сумма проверяется |
| ITD-029 | Восстановление | Полное и выборочное восстановление проверяется в отдельной области; рабочая база не перезаписывается без проверки |
| ITD-030 | Работа с потерей сети | Незавершённые изменения не теряются; конфликты выявляются; автоматическое слияние или молчаливая перезапись отсутствуют |
| ITD-031 | Уведомления и задачи | Прочтение не считается выполнением; офлайн-очередь работает; доставка не меняет статусы документов и задач |

| ITD-033 | Миграция и обновление | Перед обновлением создаётся проверенная резервная копия; миграция схемы БД сохраняет данные; возможен контролируемый откат |
| ITD-034 | Регрессия | Все ранее пройденные сценарии повторно проверены после исправлений и обновления модели/адаптера |

| AG-002 | Агент ГИП | Каждая позиция ВОР имеет доказательную привязку к ПД/РД; предположения и противоречия выделены отдельно |
| AG-003 | Агент-сметчик | Обмен сохраняет коды, шифры, наименования норм, единицы, количества и коэффициенты; преобразования явно отражены |
| AG-004 | Независимость агентов | Агентная роль работает через документированный контракт и адаптер, не обращаясь напрямую к БД конкретного клиента |
| AG-005 | Безопасность действий агента | Чтение, подготовка черновика и внешние/юридически значимые действия разграничены; значимые операции требуют подтверждения |
| AG-006 | Регрессия моделей | Замена модели/провайдера не принимается без повторного эталонного набора и проверки качества |

## 4. Обязательные негативные испытания

1. Повреждённый файл импорта не должен повредить ранее сохранённые документы.
2. Повторная загрузка того же файла не должна создавать неконтролируемый дубль.
3. Конфликтующие значения из двух источников не должны разрешаться автоматически.
4. Неуполномоченный пользователь не должен менять принятый экземпляр или статус приёмки.
5. Истечение срока согласования не должно автоматически устанавливать «Принят».
6. Изменение шаблона не должно менять ранее выпущенный документ.
7. Изменение ПД/РД не должно незаметно переписывать акт или схему.
8. Потеря сети во время записи не должна приводить к ложному сообщению об успешном сохранении.
9. Ошибка резервного копирования не должна отображаться как успешная копия.
10. Сбой обновления не должен оставлять базу в частично мигрированном состоянии.
11. Инструкция или текст из загруженного файла не должны менять правила безопасности агента.
12. Попытка агента выполнить неразрешённую отправку, публикацию, подписание или изменение статуса должна быть отклонена.

## 5. Критерии выпуска

Релиз может получить статус `QA_PASSED`, если:
- все Blocker и Critical тесты пройдены;
- все Major замечания устранены либо пользователь явно принял риск/отложил их;
- нет потери данных, несанкционированного изменения и нарушения приёмки;
- EXE/установщик запускается на чистой поддерживаемой Windows-системе;
- проверены автономный сценарий, резервирование и восстановление;
- документы формируются по подтверждённым шаблонам;
- есть отчёт с версиями, логами, результатами и перечнем `NOT_VERIFIED`.

Статус `QA_PASSED` не означает пользовательскую приёмку. Финальная приёмка и выпуск выполняются отдельно.

## 6. Форма записи результата теста

Для каждого теста фиксируются: ID, версия приложения/commit, дата, среда, тестовые данные, предусловия, шаги, ожидаемый результат, фактический результат, статус, доказательство (лог/скрин/файл/хеш), дефект и решение пользователя.

## Дополнение: испытания по исходникам «Автогенератора» (2026-11-08)

Добавить в приёмочный набор следующие сценарии:

1. **Безопасный импорт XLSM:** открыть книгу как архив OOXML; убедиться, что VBA не исполняется, исходник не изменён, скрытые листы/таблицы/имена обнаружены.
2. **Карта импорта:** сопоставить центральную таблицу актов, людей, организации, материалы, схемы, протоколы и РД с доменной моделью; неоднозначные значения показать пользователю.
3. **Связи:** проверить несколько актов на один документ качества, один акт на несколько материалов/схем/протоколов и сохранение исходного порядка.
4. **Материальные остатки:** поступление, партия, расход по нескольким актам, проверка единиц измерения и контроль отрицательного остатка.
5. **АОСР:** сформировать DOCX из редакции шаблона `АОСР.docx`; сверить обязательные формулировки, реквизиты, подписи, таблицы и страницы.
6. **Реестр ИД:** сравнить шесть граф, номера/названия документов, организацию, листность, страницу по списку и блоки сдачи/приёмки.
7. **Приложения:** отдельно сформировать реестр документов качества материалов и реестр схем/протоколов; проверить подписи и нумерацию.
8. **ОЖР:** сформировать разделы 1–6 из БД; проверить полноту и порядок записей, отсутствие зависимости от Excel-папки и Power Query.
9. **Офлайн:** отключить сеть и проверить создание/редактирование/печать документов; внешние интеграции должны завершаться понятным предупреждением, не блокируя локальные функции.
10. **Секреты:** проверить, что токены/ключи и URL лицензионных сервисов исходного продукта не попали в приложение, конфигурацию по умолчанию и репозиторий.
11. **Визуальная регрессия:** сравнить DOCX/PDF с предоставленными эталонами на уровне страниц, таблиц, переносов, колонтитулов и подписей.

## Дополнение: цифровые модели IFC/LandXML

- Импортировать IFC и LandXML как исходные файлы, не изменяя оригинал.
- Проверить определение типа модели, сохранение метаданных, версии, хеша и привязки к объекту/подобъекту.
- Проверить связь цифровой модели с ПД/РД, исполнительными схемами и документами ИД.
- Проверить, что отсутствие BIM/CIM-редактора не препятствует хранению, регистрации и передаче модели в составе комплекта.
- Проверить обработку альтернативных открытых форматов через расширяемый реестр типов, без ложного определения неподдерживаемого файла.
