# Аудит существующих GitHub-проектов как источников для приложения ИТД

**Дата:** 2026-11-08  
**Статус:** первичный статический аудит репозиториев; без изменений исходного кода и без заявления о прохождении сборки/испытаний.

## 1. Цель

До создания нового приложения проверить уже имеющиеся разработки пользователя, чтобы не дублировать работу и не выбрасывать полезный код. Разделить:
- готовые технические решения, которые можно повторно использовать после проверки;
- предметные модели и UX-решения, которые нужно перенести;
- узкоспециализированные модули, которые должны остаться отдельными или подключаться адаптером;
- устаревшие или рискованные механизмы, которые нельзя наследовать.

## 2. Проверенные репозитории

### 2.1. manager-executive-schemes

Репозиторий: https://github.com/fedor-barashkov/manager-executive-schemes  
Назначение по README: Windows-приложение для карточек строительных объектов и обновления штампов в существующих документах Microsoft Visio 2021 Desktop. Версия исходников — 2.9.1.

**Подтверждено статическим чтением файлов:**
- WPF/C# desktop application;
- проект нацелен на net8.0-windows;
- локальная SQLite через Microsoft.Data.Sqlite;
- модели ProjectCard, SchemeRecord, PageExecutorAssignment;
- таблицы Projects, Employees, Schemes;
- отдельные сервисы ProjectDatabase и VisioService;
- автоматизация Visio через COM;
- предварительная проверка структуры шаблона по Shape ID;
- предварительное открытие Visio скрыто, read-only и с отключёнными макросами (флаг 194);
- создание резервной копии перед изменением Visio-файла;
- назначение производителя работ по листам с общим значением и индивидуальными переопределениями;
- имеются PowerShell-скрипты диагностики и сборки.

**Ценность для нового приложения:**
- доказательство, что в экосистеме уже есть практическая WPF/SQLite реализация;
- готовые паттерны работы с карточками объектов, реестром схем и локальными данными;
- опыт безопасного открытия Visio только для чтения с отключёнными макросами;
- проверка шаблона до изменения, резервная копия и страничная нумерация;
- возможный исходный код отдельного адаптера Visio для связи схем с ИТД.

**Ограничения и что не переносить автоматически:**
- проект узкоспециализирован и не является полноценной системой ИТД;
- текущая модель Projects/Schemes не заменяет целевую доменную модель объектов, актов, редакций, материалов, связей и передач;
- прямые SQL-операции и EnsureColumn-подход не заменяют версионируемые миграции целевой БД;
- JSON в отдельных колонках допустим для локальных настроек, но не для основных сущностей и связей;
- COM требует установленного настольного Visio и не должен становиться обязательной зависимостью приложения ИТД;
- изменение исходного документа требует резервирования и отдельного контроля редакций;
- код не был собран и запущен в текущем аудите; заявленные проверки не считаются подтверждёнными нами.

**Решение:** использовать как референс и источник отдельных компонентов/паттернов. До повторного использования провести аудит зависимостей, лицензий, структуры, обработки ошибок, потоков COM и тестов. Не объединять репозиторий с новым продуктом и не изменять его main.

### 2.2. itd.html

Репозиторий: https://github.com/fedor-barashkov/itd.html  
Технологии по package.json и исходникам: React 18, TypeScript, Vite, Tailwind, Supabase client и другие UI-библиотеки.

**Подтверждено статическим чтением:**
- проект содержит React/TypeScript точку входа и экран выбора трёх модулей: ИТД, сметы, бизнес;
- src/types.ts включает типы объектов, заданий, смет, разделов ПД, наборов ИТД, актов ИД, журналов, сертификатов, договоров и иных сущностей;
- src/store.ts использует localStorage с ключом biznes-panel-psd и JSON import/export;
- модель данных содержит полезные названия полей и первоначальную структуру сущностей.

**Ценность:**
- источник UX-идей и структуры модулей;
- материал для инвентаризации полей и сценариев;
- типы ИТД и строительных объектов могут использоваться как черновой список кандидатов для трассировки к утверждённому ТЗ.

**Ограничения:**
- localStorage и единый JSON state не подходят как целевое транзакционное хранилище для промышленной ИТД;
- типы TypeScript не являются утверждённой доменной моделью и требуют нормализации;
- наличие Supabase client в зависимостях не означает, что сетевой backend должен быть обязательным;
- проект содержит общий экран трёх модулей, тогда как ИТД должен оставаться отдельным продуктом и репозиторием;
- исходник не следует упаковывать в EXE без переработки хранения, безопасности, версий и печатного контура.

**Решение:** сохранить как UX/functional reference; извлечь полезные поля и сценарии в матрицу требований. Не переносить localStorage как основу и не превращать приложение в общий монолит трёх программ.

### 2.3. pult-otdela

Репозиторий: https://github.com/fedor-barashkov/pult-otdela  
По README это отдельная система управления работой отдела эксплуатации с локальным сервером, SQLite, файлами, браузерными клиентами, резервными копиями и офлайн-режимом.

**Потенциальная ценность:** практический опыт локального серверного развёртывания, пользователей/ролей, резервирования, работы с файлами и распознавания документов.

**Ограничение:** описанная в README синхронизация с правилом приоритета более позднего изменения не должна переноситься без проверки на целевой конфликтный протокол. Для ИТД уже установлен принцип: конфликтующие изменения не сливать и не перезаписывать молча.

**Решение:** использовать как отдельный источник опыта по сетевому этапу и эксплуатационным сценариям, но не как основу desktop-приложения ИТД.

## 3. Важное обновление по срокам поддержки .NET

Существующий WPF-проект manager-executive-schemes нацелен на .NET 8. По официальной политике Microsoft, поддержка .NET 8 заканчивается 10 ноября 2026 года; .NET 10 LTS находится в активной поддержке до 14 ноября 2028 года. Следовательно:
- не создавать новый продукт на .NET 8;
- в spike включить проверку переноса применимых компонентов на .NET 10;
- целевой кандидат для нового WPF-приложения — .NET 10 LTS;
- успешная сборка и работа COM-интеграции после обновления должны быть подтверждены отдельно.

Официальный источник: https://dotnet.microsoft.com/en-us/platform/support/policy

## 4. Сводная матрица повторного использования

| Источник | Повторно использовать | Не переносить напрямую |
|---|---|---|
| Автогенератор ИД | Формы, последовательности, связи, алгоритмы после проверки, справочники, контрольные примеры | VBA/Power Query как runtime, внешние токены, небезопасные инструкции |
| manager-executive-schemes | WPF/SQLite паттерны, работа с карточками и схемами, проверка Visio-шаблона, резервирование, отдельный Visio adapter после аудита | Узкую схему БД как целевую модель; обязательную COM/Visio зависимость; непроверенные бинарные результаты |
| itd.html | UX, состав полей, словарь сущностей и сценариев | localStorage/единый JSON state как целевое хранилище; общий монолит 3 модулей |
| pult-otdela | Практики серверного развёртывания, ролей, backup, офлайн-поведения и OCR после аудита | Молчаливое разрешение конфликтов по принципу last-write-wins |

## 5. Вывод для архитектуры

На текущем этапе самый сильный кандидат — не «переписать всё на выбранной технологии», а создать новое доменное ядро и UI, при этом использовать проверенные части существующих решений как отдельные источники и потенциальные адаптеры.

WPF получает дополнительное практическое подтверждение за счёт уже имеющегося проекта, но это не освобождает от spike. Важно проверить перенос на поддерживаемый .NET 10 LTS, печатные формы DOCX/PDF, транзакционную БД, офлайн, резервирование и установку. Схемный Visio-модуль должен подключаться отдельно и не определять архитектуру всего приложения.

## 6. Границы аудита

Проведено чтение README, структуры каталогов и выбранных исходных файлов через GitHub. Не выполнялись:
- клонирование репозиториев в локальную среду;
- сборка проектов;
- запуск EXE;
- проверка на Windows/Visio;
- аудит всех файлов и зависимостей;
- проверка лицензий всех NuGet/npm-пакетов.

Поэтому документ фиксирует статические выводы и план дальнейшей проверки, а не сертификат качества существующих программ.
